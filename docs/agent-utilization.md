## 4. 주간 전문가 패널이 멈춘 진짜 이유

9/19 00:20Z 클라우드 루틴이 **실행됐고 `SUCCEEDED`로 끝났는데 산출물이 0**이었다.
로그를 열어 보니 원인은 명확했다.

```
curl https://naechaget.co.kr/  →  curl: (56) CONNECT tunnel failed, response 403
```

샌드박스 이그레스 정책이 우리 도메인을 막았다. 스크린샷 캡처도, 4인의 `WebFetch`도 전부
같은 이유로 불가능했다. **그 세션은 옳게 행동했다** — C.4의 "403이면 즉시 중단"을 지켰고,
근거 없는 점수를 지어내길 거부했고, 리포트를 커밋하지 않았고, 푸시 알림까지 보냈다.

> *"fabricating scores would violate the '근거 없는 지적은 싣지 않는다' rule.
> No repo changes were made."*

**실패한 것은 에이전트가 아니라 우리다.** 그 알림이 9/19에 왔는데 4일간 아무도 조치하지
않았고, 대시보드는 이 공백을 보지 못했다. §3 리듬 감시는 그래서 만들었다.

복구 절차(공식 문서 `code.claude.com/docs/en/cloud-environments` "Network access"):
클라우드 환경의 네트워크 접근을 `Trusted` → `Custom`으로 바꾸고 허용 도메인에
`naechaget.co.kr`을 추가한다. **API로는 안 되고 화면에서만 된다.** → §5-⑤

### ★ 그런데 더 먼저인 것이 있었다 — 알림이 꺼져 있었다 (2026-09-23 조치 완료)

루틴 화면의 `세부 정보`가 **`알림 끔`** 이었다. 정기 작업의 알림을 꺼 두면 실패가 조용히
지나간다 — 9/19 실패를 4일간 아무도 모른 데에 이것이 기여했을 가능성이 크다.
(그날 세션이 푸시를 한 번 요청한 기록은 있으나 전달 여부는 확인할 수 없어, **원인이
이것뿐이라고 단정하지는 않는다.**) 오너가 **`Push 알림 켜짐`** 으로 바꿨다.

### 조치 결과 — 도메인은 뚫렸고, 대신 `pip` 이 막혔다 (2026-09-23)

오너가 새 클라우드 환경 `naechaget-panel` 을 만들어 네트워크 접근을 `신뢰됨` → `사용자 지정`
으로 바꾸고 `naechaget.co.kr` 을 허용했다(`Default` 환경은 편집이 막혀 있어 새로 만들어야 했다).
루틴을 그 환경으로 옮긴 뒤 즉시 실행해 **403 이 사라진 것을 실측으로 확인**했다.

```
curl https://naechaget.co.kr/vehicle/doesnotexist_1  →  303   (9/19 에는 403)
curl https://naechaget.co.kr/accuracy                →  200
WebFetch https://naechaget.co.kr/courts              →  200
```

**그런데 이번엔 `pip install playwright` 가 실패했다.** 디자인 전문가가 리포트 첫 줄에
*"playwright 설치 실패로 스크린샷을 확보하지 못했다 … 320~1440px 육안 검수는 불가능했다"*
라고 적었다. 9/19 실행(`신뢰됨`)에서는 같은 설치가 **성공**했다.

→ **추정**: `사용자 지정` 으로 바꾸면서 기본 패키지 관리자 허용목록(pypi 등)이 함께 빠졌다.
실패 메시지 원문은 확인하지 않았다(로그 페이지 비용이 커서 받지 않았다). **확정이 아니다.**
확인 방법은 환경 설정 화면에서 '기본 패키지 목록 포함' 체크 여부를 보는 것뿐이다.

교훈: **한 곳을 열면 다른 곳이 닫힐 수 있다.** 네트워크 정책을 바꾸면 바꾼 것만 보지 말고
**그 전에 되던 것이 아직 되는지** 확인해야 한다. 이번엔 패널이 절반만 일했다 —
라이브 평가는 했고 화면 검수는 못 했다.

교훈은 도메인 문제와 별개다: **정해진 리듬에는 알림이 켜져 있어야 한다.**
안 도는 것보다 나쁜 것이 '돌았는데 아무것도 안 남기고 아무도 모르는 것'이다.
§3 리듬 감시는 알림이 또 꺼지더라도 **산출물의 나이로** 같은 공백을 잡아내기 위한 이중 장치다.

## 6. 이 점검에서 내가 틀렸던 것

기록해 둔다. 같은 방식으로 또 틀리지 않기 위해서다.

1. **"전문가 자리를 두고 범용에 시켰다 — 내 잘못"** → 틀렸다. SKILL.md에 적힌 정식 우회로였다.
2. **"주간 패널이 11일째 안 돌았다"** → 틀렸다. 9/19에 돌았고, 막혀서 아무것도 못 남겼다.
3. **"스킬 파일이 origin/main에 없다"** → 틀렸다. `git cat-file` 검사가 거짓음성이었고,
   실제로는 추적 중이며 클라우드 clone도 정상적으로 읽었다.
4. **"상위 3인 점유율 84%"** → 틀렸다. 실제는 **80.3%**. 집계 스크립트가 분자에는
   로스터 밖 `general-purpose` 7회를 섞고 분모는 로스터 61회만 썼다 —
   **분자와 분모가 다른 집합이었다.** 대시보드가 같은 값을 다시 재서 드러났다.

5. **"CSS 주석이 167줄에서 닫히지 않았다"** → 틀렸다. 그 주석은 171줄에서 정상적으로
   닫힌다. 내 검사기가 `/*`·`*/` 개수를 단순히 센 탓인데, **주석 본문 안에**
   `docs/reviews/persona/*.md` 가 들어 있어 그 `/` + `*` 가 '여는 괄호'로 세어졌다 —
   320px 버그를 설명하려고 쓴 주석의 예시 경로가 내 검사기를 속였다.
   브라우저가 규칙 **96개**를 정상 파싱하고 그 주석 뒤의 `.cols>*`·`.empty`·`footer` 가
   전부 살아 있음을 확인해 뒤집었다. **CSS가 아니라 검사기가 틀렸다.**
6. **"리듬 표의 `1일` 칸만 색이 다르다"** → 틀렸다. 계산된 색이 다섯 칸 모두
   `rgb(230,237,243)` 로 동일했다. 축소된 PNG의 렌더링 아티팩트를 결함으로 읽었다.

1~3은 **한 지표를 보고 원인을 단정**한 것, 4는 **집계 범위를 확인하지 않은 것**,
5~6은 **검사 도구와 축소 이미지를 그대로 믿은 것**이다. 여섯 다 재현해 보고서야 뒤집혔다.

그리고 오늘 측정은 내 눈을 **양방향으로** 이겼다 — 멀쩡해 보이던 업무 분포 막대는 실제로
채움 **0px** 이었고(`.fill` 이 인라인 span 이라 `width:100%` 가 무시됐다), 고장나 보이던
`1일` 칸은 멀쩡했다. 그래서 규칙은 하나다: **눈으로 본 것은 단서이고, 계산된 값이 증거다.**
이 화면이 모든 수치에 '무엇을 어떤 범위에서 셌는지'를 붙여 적는 이유도 같다.
