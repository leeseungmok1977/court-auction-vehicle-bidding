## 3. 리듬 감시 — 정해진 주기가 실제로 도는가

**끊긴 것을 아무도 못 봤다는 게 이번 점검의 가장 큰 수확이다.** `docs/reviews/`가 11일째
멈춰 있었는데 대시보드는 초록이었다. 그래서 산출물의 나이를 직접 잰다.

`주기`를 넘기면 `늦음`, 두 배를 넘기면 `끊김`. `시작`은 **그 전에는 없어도 정상**인 날짜다
(첫 실행 전인 것을 실패로 세면 안 된다 — 2026-09-23에 실제로 그렇게 오판했다).

| 산출물 | 주기 | 시작 | 담당 | 끊기면 무엇이 멈추나 |
|---|---|---|---|---|
| `docs/reviews/*.md` | 7 | 2026-09-12 | 전문가 4인 | 주간 보고의 전문가 점수 칸이 빈다 |
| `docs/reviews/persona/*.md` | 7 | 2026-09-11 | (담당 없음 — §5-④) | 세그먼트별 사용성 격차 추적이 끊긴다 |

| `docs/weekly-reports/*.md` | 7 | 2026-09-26 | (자동 토 13:00) | 제품 지표 추세를 못 본다 |
| `docs/monthly-reports/*.md` | 30 | 2026-10-01 | (자동 1일 13:30) | 손익·전략 점검이 끊긴다 |

> `docs/reviews/persona/`의 주기 7일은 **헌장 규정이 아니라 운영 목표**다. 실측 간격은
> 9/11 → 9/14 → 9/17 로 3일이었고 그 뒤 멈췄다.

### ⚠ 이 감시 장치의 구멍 — 내가 파일을 쓰면 초록이 된다

2026-09-23 실제로 목격했다. `리듬 이상`이 **1/5 → 0/5** 로 바뀌었는데, 패널이 되살아나서가
아니라 **내가 6회차 복구본을 손으로 써 넣었기 때문**이다. 이번엔 실제로 돌았던 회차를 옮겨
적은 것이라 내용은 정직하지만, 구조적으로 이 장치는 **"의식이 실제로 돌았는가"가 아니라
"파일이 최근인가"** 만 본다.

그래서 이 장치는 **조용한 실패를 잡되, 사람이 대신 채워 넣는 것은 못 잡는다.**
작성자·커밋 주체까지 검증하는 방법도 있지만 1인 회사에 과하다고 판단했다.
대신 규칙 하나를 둔다 — **리듬을 만족시키려고 파일을 쓰지 않는다.**
기록할 것이 실제로 있을 때만 쓰고, 복구본은 **맨 위에 복구본이라고 박는다**
(`docs/reviews/2026-09-22.md` 가 그 예다).

## 4. 주간 전문가 패널이 멈춘 진짜 이유

9/19 00:20Z 클라우드 루틴이 **실행됐고 `SUCCEEDED`로 끝났는데 산출물이 0**이었다.
로그를 열어 보니 원인은 명확했다.

```
curl https://naechaget.co.kr/  →  curl: (56) CONNECT tunnel failed, response 403
```

샌드박스 이그레스 정책이 우리 도메인을 막았다. 스크린샷 캡처도, 4인의 `WebFetch`도 전부
같은 이유로 불가능했다. **그 세션은 옳게 행동했다** — C.4의 "403이면 즉시 중단"을 지켰고,
근거 없는 점수를 지어내길 거부했고, 리포트를 커밋하지 않았고, 푸시 알림까지 보냈다.

> *"fabricating scores would violate the '근거 없는 지적은 싣지 않는다' rule.
> No repo changes were made."*

**실패한 것은 에이전트가 아니라 우리다.** 그 알림이 9/19에 왔는데 4일간 아무도 조치하지
않았고, 대시보드는 이 공백을 보지 못했다. §3 리듬 감시는 그래서 만들었다.

복구 절차(공식 문서 `code.claude.com/docs/en/cloud-environments` "Network access"):
클라우드 환경의 네트워크 접근을 `Trusted` → `Custom`으로 바꾸고 허용 도메인에
`naechaget.co.kr`을 추가한다. **API로는 안 되고 화면에서만 된다.** → §5-⑤

### ★ 그런데 더 먼저인 것이 있었다 — 알림이 꺼져 있었다 (2026-09-23 조치 완료)

루틴 화면의 `세부 정보`가 **`알림 끔`** 이었다. 정기 작업의 알림을 꺼 두면 실패가 조용히
지나간다 — 9/19 실패를 4일간 아무도 모른 데에 이것이 기여했을 가능성이 크다.
(그날 세션이 푸시를 한 번 요청한 기록은 있으나 전달 여부는 확인할 수 없어, **원인이
이것뿐이라고 단정하지는 않는다.**) 오너가 **`Push 알림 켜짐`** 으로 바꿨다.

### 조치 결과 — 도메인은 뚫렸고, 대신 `pip` 이 막혔다 (2026-09-23)

오너가 새 클라우드 환경 `naechaget-panel` 을 만들어 네트워크 접근을 `신뢰됨` → `사용자 지정`

루틴을 그 환경으로 옮긴 뒤 즉시 실행해 **403 이 사라진 것을 실측으로 확인**했다.

**그런데 이번엔 `pip install playwright` 가 실패했다.** 디자인 전문가가 리포트 첫 줄에

라고 적었다. 9/19 실행(`신뢰됨`)에서는 같은 설치가 **성공**했다.

**2026-09-23 정정 — 이 추정은 틀렸다.** 실행 로그의 품질 전문가 보고서 원문은 이렇다:

**오늘 같은 실수를 다섯 번째 반복한 것이다**(§6 참조) — 비용이 아까워 원문 확인을 미룬 것이
원인이었는데, 원문 한 번 보는 값이 틀린 지시를 내리는 값보다 쌌다.

교훈: **한 곳을 열면 다른 곳이 닫힐 수 있다.** 실제로 이번 실행은 문을 **세 개** 지나야 했다 —
이그레스(뚫림) → 도구 권한(막힘, 설치 실패) → GitHub 쓰기 권한(막힘, 푸시 403).
하나를 고치면 그다음 문이 드러난다. 그래서 판정은 **끝까지 간 산출물**로만 해야 한다.

### ② 의 진짜 증상 — '완료'인데 아무것도 안 깔렸다

```
23:32:17.347  Running setup script
23:32:18.613  Setup script completed      ← 1.27초
```

`requirements.txt` 에는 `onnxruntime`(약 200MB)·`numpy`·`Pillow` 가 있다. 실제로 설치했다면
**수십 초**가 걸린다. 1.27초는 **즉시 실패**했다는 뜻이고, 실행 후 확인도 그랬다 —
`No module named pytest`, `pip show playwright` → 없음.

**내가 붙이라고 한 `|| true` 가 실패를 삼켰다.** 세션이 뜨지 못하는 것을 막으려던 장치가
**진단을 지웠다.** 안전장치를 걸 때는 *무엇을 가리게 되는지*도 같이 봐야 한다.

~~1.27초에 끝날 만한 원인은 셋이고 어느 것인지 모른다~~
**2026-09-23 확정 — 셋 다 아니었다.** 검증 실행(`cse_01FfqR3h…`)의 로그에 원문이 남았다.

```
python3 -m pip install -q -r requirements.txt
→ ERROR: Cannot uninstall PyYAML 6.0.1, RECORD file not found.
  Hint: The package was installed by debian.
```

`PyYAML` 이 **데비안 패키지로 깔려 있어 pip 이 제거하지 못하고 거기서 통째로 중단**된다.
`requirements.txt` 가 그 줄에서 멈추니 **명령 맨 뒤의 `playwright` 는 영영 설치되지 않는다.**
어제 1.27초도 같은 이유다.

그래서 이번 세션은 필요한 것을 **하나씩 우회 설치**해 `pytest` 를 살려냈고(전 항목 통과까지
확인), `playwright` 만 끝내 못 깔아 **스크린샷이 2회 연속 0장**이 됐다.

고치는 방법은 **플래그 하나**다 — 그 패키지만 건드리지 말라고 일러 준다.

```bash
#!/bin/bash
R=/home/user/court-auction-vehicle-bidding/requirements.txt
python3 -m pip install --break-system-packages --ignore-installed PyYAML -r "$R" playwright ||
python3 -m pip install --ignore-installed PyYAML -r "$R" playwright
exit 0
```

**교훈**: 나는 `EXIT:0` 과 `Setup script completed` 를 보고 "설치가 됐다"고 읽었다.
`pip` 은 **실패해도 0 을 돌려준다.** 종료 코드가 아니라 **결과물**(`import` 가 되는가)로
확인해야 했다. 오늘 내가 반복해서 배운 것과 같은 규칙이다 —
**상태값이 아니라 산출물로 판정한다.**

### 검증 실행의 결과 (2026-09-23 00:05~00:26Z)

| ③ GitHub 쓰기 | **또 403** — 리포트가 `af000c9` 로 커밋됐다가 샌드박스와 함께 사라짐 |

```bash
python3 -m pip install -r "$R" playwright

```

## 6. 이 점검에서 내가 틀렸던 것

1. **"전문가 자리를 두고 범용에 시켰다 — 내 잘못"** → 틀렸다. SKILL.md에 적힌 정식 우회로였다.

3. **"스킬 파일이 origin/main에 없다"** → 틀렸다. `git cat-file` 검사가 거짓음성이었고,
   실제로는 추적 중이며 클라우드 clone도 정상적으로 읽었다.

5. **"CSS 주석이 167줄에서 닫히지 않았다"** → 틀렸다. 그 주석은 171줄에서 정상적으로
