## 0. 이 조사가 서 있는 자리 (반드시 먼저 읽을 것)

- **이 앱은 행동 지표를 수집하지 않는다**(`docs/ORG.md` §4·§5, Play 데이터 안전 "수집된 데이터
  없음"). 그래서 "어느 화면에서 헤맸는지·왜 포기했는지" 같은 사용성 질문은 클릭 로그로 대조할
  방법이 없다. **이 설문의 답변이 그 질문에 대한 유일한 근거**다 — 나중에 "실제로는 이랬을
  것"이라고 행동 데이터로 보정할 수 없다는 뜻이다.
- `bidder-insight`(외부, 아직 우리 사용자가 아닌 사람 6건)와 이 설문(내부, 최대 12명 실사용
  테스터)은 **표본 모집단이 다르다.** 심리 6범주 어휘(기회추구·불확실성불안·경쟁과열·손실회피·
  사회적증거·통제감)는 두 조사가 공유하되, **숫자를 합산하지 않는다.** voice가 이후 이 설문을
  정리할 때는 항상 "테스터 n명 중 m명"으로만 쓰고 bidder-insight의 6건과 더하지 않는다.
- 모수: **12명**(Play Console 대시보드 실측, PLAY-1 티켓). 응답률은 오너가 실제 답장을 받은
  뒤에만 안다 — 지금은 **발송 전, 응답 0건**이다. 회수 결과를 부풀려 "테스터들이 원한다"고
  쓰지 않는다.
- "5분 이내"는 질문 5개·혼합형(객관식+짧은 주관식) 분량을 기준으로 한 **설계 목표이지 실측이
  아니다.** 실제 소요 시간은 재지 않았다.
- **compliance-officer 판정(2026-09-26)**: Play '데이터 안전'의 수집 정의는 앱에서 기기 밖으로
  전송되는 데이터이므로 앱을 거치지 않는 카카오톡 1:1 설문은 신고 범위 밖이며 '수집된 데이터
  없음' 신고와 충돌하지 않는다. 조건 셋 — ① 설문을 앱 화면·앱 내 링크·스토어 등록정보에서
  연결하지 않는다 ② 답변·요지·라벨 행을 서버 경로나 운영 DB에 두지 않는다 ③ `/privacy`를 이
  설문 때문에 고치지 않는다. 근거·한계는 `docs/compliance-review.md` §11.
- **발송 전 확인**: 오너가 수신자 12명 전원의 만 14세 미만 여부를 확인한다(가족 포함). 만
  14세 미만에게는 발송하지 않는다. 만 14~19세 미만은 제외를 권고한다(선택, 오너 결정).

## ① 카카오톡 발송 문구 — 그대로 복사해 보내면 된다

공백·개행 포함 **실측 481자**(python `len()` 기준, 목표 500자 이내 충족). 어조는 기존 테스터
모집 문구(`docs/CLOSED_TESTING_GUIDE.md` "2. 테스터에게 보낼 문구")와 동일하게 1인칭·존댓말·
이모지 최소로 맞췄다. 마지막 문단은 `compliance-officer` 반려(R1, `docs/compliance-review.md`
§11)에 따라 **보유기간·동의 문구를 명시**하도록 다시 썼다.

```
[내차GET 짧은 설문 — 5분만 부탁드립니다]

2주 테스트 감사했습니다. 출시를 앞두고 다음 방향을 정하려 몇 가지만 여쭤요. 어려운 질문은 건너뛰셔도 됩니다.

1. 경매차 알아볼 때 가장 막막했던 것은? ①차 상태 확인 ②적정가 판단 ③서류·절차 ④기타
2. 얼마를 써낼지 어떻게 정하실 것 같나요? 무엇이 있으면 정하기 쉬울까요? (자유롭게)
3. 낙찰받은 뒤 가장 걱정되는 것 한 가지는?
4. 앱에서 뜻을 모르거나 찾다가 포기한 화면·용어가 있었나요? ①있음(무엇인지) ②없음
5. 돈 내고서라도 쓰고 싶은 기능이 딱 하나 있다면?

답변은 내차GET 앱 개선과 정식 출시 준비에만 쓰고, 저희 정리 자료에는 성함·연락처 없이 요지만 남겼다가 6개월 안에 지웁니다. 안 하셔도 불이익 없고, 언제든 "삭제해주세요"라고 주시면 제가 받은 답장과 정리 자료에서 지우고 알려드리겠습니다. 위 내용에 동의하시면 이 채팅에 편하게 답장 주세요. 감사합니다.
```

**발송 방식 참고**: 위는 한 번에 보내는 안이다. 답장이 부담스러워 보이면 1~5를 서너 번에
나눠 보내도 무방하다(내용은 동일). 어느 쪽이 응답률이 높은지는 **모른다** — 실험한 적 없다.

## ② 질문 설계 근거 (문구 안에는 번호만 노출, 아래는 내부 기록용)

| # | 단계 (지시서 원문) | `bidder-insight` 프레임 매핑 | 형식 | 리딩 질문 방지 |
|---|---|---|---|---|
| 1 | 탐색 — 가장 막막했던 것 | 탐색 단계, 불확실성불안·사회적증거 후보 | 객관식(①~③)+기타 주관식 | 세 선택지를 문제 영역별로 병렬 제시, 우리 기능 이름을 선택지에 넣지 않음 |
| 2 | 입찰준비 — 얼마를 어떻게 정할지 / 무엇이 있으면 정하겠는지 | 입찰준비 단계, 기회추구·손실회피 후보 | 순수 주관식(두 하위 질문을 한 문장에) | "우리 리포트가 도움이 됐나요"처럼 자기 제품을 먼저 들이밀지 않고 중립적으로 물음 |

| 4 | 앱 — 이해 안 됐거나 찾다가 포기한 것 | 새 축(사용성) — 원 5단계 밖 | 객관식(있음/없음)+있으면 주관식 | "어디가 불편했나요"가 아니라 "이해가 안 됐거나 포기했나요"로 한정해 막연한 불만 유도를 줄임 |

## ③ 동의 문구 — 정식판 (compliance-officer 확정)

메시지 ①에는 요약(굵게 표시된 한 문장)만 넣었다. 아래는 그 문장이 실제로 보장해야 하는 내용을
6개 항목으로 풀어 쓴 정식판이다 — 표현은 `compliance-officer`가 반려 사유(R2, §11) 반영 후
확정했다.

```
- 용도: 내차GET 앱 개선 검토와 정식 출시 준비에만 씁니다. 정식 출시 준비에는 구글 플레이 프로덕션 액세스 신청서의 "테스터 피드백" 서술에 성함 없는 요지를 인용하는 것이 포함됩니다. 스토어 설명·랜딩·SNS·마케팅 문구에는 수치도 인용도 쓰지 않습니다.
- 남기는 것: 답변을 정리 자료에 남길 때 성함·연락처·카카오톡 프로필·답장 시각을 빼고 요지만 남깁니다. 다만 1:1 대화라 저는 누구의 답인지 알고 있으므로 "익명"은 아니며, 정리된 요지도 개인정보로 다뤄 아래 기간·삭제 약속을 지킵니다.
- 보관 기간: 답장 원문 붙여넣기는 요지 정리 즉시 지우고, 정리된 요지는 받은 날부터 180일 안에 지웁니다. 집계 숫자("n명 중 m명")만 남습니다.
- 거부·철회: 답하지 않거나 일부만 답해도 테스트 참여 자격과 무관하며 어떤 불이익도 없습니다. 언제든 "삭제해주세요"라고 답장 주시면 제가 받은 답변과 정리 자료에서 지우고 알려드립니다.
- 제공·이전: 답변 요지는 제가 앱 개선 검토에 쓰는 AI 도구에 성함 없이 넣어 분류합니다. 그 밖의 외부 제공은 없습니다.
- 대상: 만 14세 미만 분께는 보내지 않습니다.
```

**compliance-officer 확정(2026-09-26)**: '익명'·'익명 설문'·'익명 답변'·'완전 익명'을 쓰지
않는다. 카카오톡 1:1 대화라 오너가 답변자가 누구인지 알고 있어 재식별이 가능하므로, 내부
표기는 **가명 라벨(T1~T12)·성함 미기재**로 통일하고 정리된 요지도 개인정보(가명처리)로
취급한다. 근거: `docs/compliance-review.md` §11.

## ④ 답변 정리 규칙 (오너 → voice 전달 이후)

1. 오너가 카카오톡 답장에서 성함·프로필·답장 시각·결합 식별 요소(직업·거주지·가족관계·금액·
   차량번호·사건번호)를 먼저 지운 뒤, 라벨 `T1`~`T12`를 붙여 스크래치 파일로 voice에 전달한다.
   voice는 라벨과 답변 본문만 받으며 실명·프로필·시각을 받지 않는다. 저장소(`reports/`·`data/`
   등 영구 경로)에 원문 그대로 커밋·저장하지 않는다.
2. 라벨↔실명 매핑은 오너가 저장소 밖(폰 메모 등 1곳)에 보관기간(180일) 동안만 보관하고 만료
   시 지운다. 삭제 요청이 오면 어느 행을 지울지 이 매핑으로 찾는다.
3. 질문마다 아래 필드만 남긴다(`bidder-insight`의 항목 스키마를 재사용하되 소스를 분리):
   ```json
   {
     "tester_label": "T1",
     "stage": "탐색|입찰준비|낙찰후|앱사용성|지불의향",
     "psychology": ["기회추구|불확실성불안|경쟁과열|손실회피|사회적증거|통제감 중 근거가 뚜렷할 때만, 없으면 생략"],
     "answer_summary": "30자 내외 요약 — 답장 원문을 길게 옮기지 않는다",
     "unmet_need": "원했지만 없었던 정보·기능, 없으면 null",
     "money_risk": true,
     "wtp_feature": "5번 답변 요지, 없으면 null",
     "source": "tester_survey_2026-09",
     "collected_on": "YYYY-MM-DD",
     "delete_by": "collected_on + 180일"
   }
   ```
   `source` 필드로 `bidder-insight`의 `클리앙|뽐뿌|블로그`와 항상 구분되게 한다. `collected_on`은
   오너가 답장을 받은 날짜, `delete_by`는 그로부터 180일 뒤다.

   요지 자유문(`answer_summary`·`unmet_need`·`wtp_feature`)에 넣지 않는 것: ① 법 제23조
   민감정보(건강·정치·종교 등) ② 금액(예산·대출·연봉) ③ 가족관계·직업·거주지 ④ 차량번호·
   사건번호·특정 물건. 이런 내용이 섞여 있으면 요지 자유문을 비우고(`null`) `stage`·
   `psychology`·`money_risk` 같은 코드값만 남긴다.
4. **저장 위치를 분리한다.** `T1`~`T12` 라벨 행(JSON, 요지 자유문 포함)은 **git 밖**(스크래치
   파일 또는 `.gitignore`된 `data/`)에만 두고 `delete_by`가 되면 지운다. 저장소에 커밋하는
   `reports/tester-survey-YYYY-MM-DD.md`에는 `bidder-insight`와 같은 절 구성
   ([모집단]·[범주별 빈도]·[미충족 니즈]·[우리 화면과 대조]·[제안]·[한계])으로 쓰되 **집계·
   코드값·주제 서술만** 남기고, 표 제목에 반드시 **"테스터(우리 사용자) n건"**이라고 적어
   bidder-insight의 "잠재고객 n건"과 한눈에 구분되게 한다. 두 표를 같은 열에 합산하지 않는다.
   프로덕션 액세스 신청서 인용도 **라벨 없이 주제 단위로만** 쓴다.
5. 표본이 작다(최대 12명) — **%를 쓰지 않고 "n명 중 m명"만 쓴다.**
6. 원문(카카오톡 대화 붙여넣기)은 분류 완료 즉시 스크래치 파일에서 삭제한다. `T1`~`T12` 라벨
   행(JSON)은 git 밖 위치에만 남기고 `delete_by`에 지운다. git에 커밋하는 리포트 문서에는
   라벨 행·요지 자유문을 넣지 않고 집계·코드값·주제 서술만 남긴다.
7. **compliance-officer 확정(2026-09-26)**: 보관 기간은 원문(카카오톡 붙여넣기) **0일**(정리
   즉시 삭제) / 라벨 행 **180일**(`delete_by`, git 밖 저장) / 오너 기기에 남는 카카오톡 원문
   대화는 삭제 요청이 오면 **반드시** 지우고, 180일이 지난 뒤 선제적으로 지우는 것은
   **오너 결정(권고)**이다.
8. **결과물의 사용 범위**: 설문 결과(수치·인용·"테스터 n명이 원했다")는 내부 리포트·제품
   개선·프로덕션 액세스 신청서에만 쓴다. 스토어 설명·랜딩·블로그·SNS·유료 전환 문구에는 쓰지
   않는다. 5번(지불의향) 답변을 요금제 홍보 문구 근거로 외부 인용하는 것은 금지한다.
