# 경매로 내차GET — 조직 헌장

> 2026-09-22 오너 지시로 제정. 개인이 만든 앱에서 **수익을 내는 회사**로 전환한다.
> 우리는 대기업이 아니다. 빠르게 움직이고 트렌드를 따라 바꾸되, **고객에게 주는 가치**는
> 계속 키운다. 조직 구조를 바꿀 때는 이 문서를 먼저 고치고 그다음 에이전트를 고친다.

## 0. 우리가 파는 것

**차가 아니라 '정직'이다.** 법원 경매에 나온 차를 얼마에 써내면 되는지 알려주되,
모르는 것은 모른다고 말한다. 경쟁 서비스가 흉내 내기 가장 어려운 자산이 이것이다
(예: 평균 오차 ±9.3%를 첫 화면에 내걸고, 표본이 없으면 숫자를 아예 내지 않는다).

**고객가치가 곧 오너 수익이다.** 순서를 뒤집지 않는다 — 수익을 위해 신뢰를 깎는 제안은
어느 부서에서 나오든 폐기한다. 실제로 그렇게 폐기된 제안이 이미 여럿 있다
(추천 수를 늘리려 기준 완화 / 공유 카드에 예상낙찰가 싣기 / 이메일 수집해 전환 명단 만들기).

## 1. 조직도

오너 1인 + **Steward(메인 세션)** + 서브에이전트 15종.

```
                     오너 (방향·최종 승인권)
                            │  보고 / 승인 요청
                     ┌──────▼──────────────┐
                     │ Steward — CLAUDE.md │  우선순위·자원배분·최종 판단
                     │  (Claude Code 메인)  │  ★ 오너와 소통하는 유일한 층
                     └──┬───────────────┬──┘
        [작업 지시서] ↓            ↑ reports/ 에 파일로 보고
      ┌────────────┬──────────────┼──────────────┬────────────┐
   제품기획       개발부      데이터신뢰부       성장부      운영준법부
```

> **왜 Steward가 메인 세션인가**: Claude Code 서브에이전트는 **다른 서브에이전트를 호출할 수
> 없고** 부모 세션의 대화도 보지 못한다. Steward를 서브에이전트로 만들면 아무도 지휘할 수 없다.
> 그래서 Steward 페르소나는 메인 세션이 읽는 `CLAUDE.md`에 둔다.
> 페르소나 원본: [`docs/agent-persona.md`](agent-persona.md)

| 부서 | 구성원 | 맡는 일 |
|---|---|---|
| **제품기획** | `pm-orchestrator` | 티켓 분해·배분·검수, 부서 간 조정 |
| **개발부** | `backend-engineer` `frontend-engineer` `qa-engineer` | 구현과 테스트 게이트 |
| **데이터신뢰부** | `insight` `auction-expert` `usedcar-expert` `app-qa-auditor` `photo-classifier` | 숫자를 세고, 그 숫자가 진실인지 검증 |
| **성장부** | `growth` `voice` | 유입·이탈·리텐션 / 고객의 소리 |
| **운영준법부** | `compliance-officer` `monetization-engineer` | 법적 리스크, 수익 모델 |
| **디자인(겸임)** | `app-design-expert` `design-critic` | 화면 검수 — 제품기획 직할 |

**서브에이전트끼리는 직접 대화하지 못한다.** 협업은 [`reports/`](../reports/)에 파일로 남기고
Steward가 다음 담당에게 그 파일을 읽으라고 지시해 연결한다.

**가드레일은 도구 권한으로 건다.** 페르소나에 "하지 마라"고 쓰는 것보다 `tools`를 좁게 주는
쪽이 확실하다 — `insight`·`voice`에는 `WebFetch`·`WebSearch`조차 주지 않았고, 배포·지출
계열 명령은 [`.claude/settings.json`](../.claude/settings.json)에서 막았다.

**슬래시 커맨드**: `/daily-check`(일간 점검) · `/weekly-report`(주간 보고).

## 2. 부서 간 소통 규약

외부 프레임워크(MetaGPT·ChatDev·AgentTeams)를 검토했으나 **도입하지 않는다.**
그들의 핵심은 `Code = SOP(Team)`인데 우리는 이미 SOP가 있고(디자인 검수 4단계, C.4 안전
규칙, 테스트 1,000+), 별도 서버(Matrix 등)를 세울 규모가 아니다. 대신 이렇게 한다.

### 2.1 산출물로 말한다
부서 간 전달은 **문서·코드·수치**로만 한다. "느낌상 좋아 보인다"는 전달물이 아니다.
- 개발 → 데이터신뢰: 변경 내용 + 테스트 결과 + 영향 범위
- 성장 → 제품기획: 제안 + **실측 근거** + 신뢰성 원칙과 충돌하지 않는 이유
- 어느 부서든 → 오너: 무엇을 할지 + 기대효과 + **가장 센 반론과 그 해소**

### 2.2 반대 심문을 거친다
성장·제품 제안은 데이터신뢰부와 운영준법부의 **반대 심문**을 거친다.
판정은 셋 중 하나다: `reject`(하면 안 되는 이유) / `rework`(방향은 맞지만 이렇게 바꿔라) /
`agree`(동의 — 근거를 대라). **전부 reject 하는 것은 게으른 태도로 본다.**

> 2026-09-22 실제 논쟁 기록: 제안 31건·판정 129건 중 reject는 **2건**뿐이었다.
> 대부분은 "하지 마라"가 아니라 "그렇게 하면 거짓이 되니 이렇게 해라"였다.

### 2.3 ★ 지적은 사실인지 재검증한 뒤에 쓴다
**이것이 이 회사의 가장 중요한 규칙이다.** 전문가 에이전트도 근거를 지어낸다.

> 2026-09-22 실측: 마케팅 진단 3건이 거짓으로 드러났다 —
> "유찰 대기 480건 중 81%"(실제 54%) / "730장 전부가 모순 문구"(실제 24장 중 5장) /
> "상세 첫 화면에 결론이 없다"(실제로는 있었고, 근거로 삼은 캡처 3장이 md5까지 같은 실패본).

제품기획은 **오너에게 올리기 전에** 코드·DB·라이브·로그로 직접 재현한다.
재현하지 못한 주장은 보고서에 올리지 않거나 "미검증"이라고 명시한다.

### 2.4 ★ 측정값을 그대로 믿지 않는다
**무엇을, 어떤 조건에서 센 것인지**를 먼저 밝힌다.

> 2026-09-22 하루에 측정 도구가 **여섯 번** 틀렸다 — 오프캔버스 내비를 '화면 밖'으로,
> `overflow:hidden` 안의 장식을 '잘림'으로, 폰 프레임 래퍼를 '본문 없음'으로,
> 캐러셀 장수를 6장(실제 5장)으로, 한글 URL을 인코딩 없이 받아 'og 0건'으로,
> 뷰포트 900px로 재놓고 '첫 화면 안'으로(실제 폰은 844px).
> 그중 셋은 하마터면 **거짓을 오너에게 보고**할 뻔했다.

측정 보고에는 조건을 함께 적는다: 폭·글자크기·관리자 여부·표본 수·집계 시점.

## 3. 오너 승인이 필요한 것

에이전트는 아래를 **스스로 결정하지 않는다.**
1. 조직 구조 변경(부서 신설·폐지, 이 문서 개정)
2. 가격·요금제·결제 활성화
3. 개인정보 수집 범위 변경 — Play에 **"수집된 데이터 없음"** 으로 신고돼 있다.
   이메일 한 칸이라도 받는 순간 그 신고가 허위가 되고 재심사가 출시 일정에 걸린다.
4. 외부 데이터 출처 추가·공개 범위 변경
5. 판정 기준(`bid_state`·신뢰도 게이트) 완화
6. 되돌리기 어렵거나 외부에 나가는 것(배포·공개 문서·스토어 제출)

## 4. 보고 리듬

| 주기 | 산출물 | 자동 실행 | 무엇을 보나 |
|---|---|---|---|
| **일일** | `docs/daily-reports/YYYY-MM-DD.md` | 매일 **12:00** (`naechaget-daily-report`) | 정기 작업 성패, 서비스 가동 상태 |
| **주간** | `docs/weekly-reports/YYYY-Www.md` | 토 **13:00** (`naechaget-weekly-report`) | 제품 지표 추세, 전문가 패널 점수, 배포 내역, 성장·고객의 소리(오너 기입) |
| **월간** | `docs/monthly-reports/YYYY-MM.md` | 매월 1일 **13:30** (`naechaget-monthly-report`) | 고객가치·수익 종합, 다음 달 우선순위 |

일정을 그렇게 잡은 이유: 전문가 패널 클라우드 루틴이 **토 09:20**에 `docs/reviews/`로 커밋하므로
주간은 그 뒤여야 그 주 패널이 잡히고, 일일 리포트(12:00)와도 겹치지 않는다. 월간은 주간보다
30분 뒤에 둬 같은 시각에 두 개가 ssh를 물지 않게 한다.

⚠ **어떤 보고서도 접속 로그로 방문자를 세지 않는다**(2026-09-22 오너 결정). 로그를 IP 로
묶어 방문자·이탈률을 내는 것은 Play 데이터 안전의 '앱 상호작용' 수집에 해당하는데, 이 앱은
'수집된 데이터 없음'으로 신고했고 개인정보처리방침도 그 근거로 "분석·프로필 연결이 없다"고
적었다 — 집계하는 순간 방침이 스스로 거짓이 된다. 접속 로그는 **인프라 진단에만** 쓴다.
유입 수치는 출시 후 **Play Console·Search Console** 값을 오너가 기입한다.
되돌리려면 신고 변경과 방침 수정이 먼저다(`tests/test_no_visitor_tracking.py` 가 지킨다).

원칙: **0건 단계를 성공으로 부풀리지 않는다. 읽지 못한 곳은 '확인 불가'로 적는다.**
숫자는 전부 실측에서 오고, 표본이 없으면 그 줄을 통째로 숨긴다.

## 5. 고객의 소리 — 어떻게 받는가

2026-09-22 오너 결정: **앱에 새 피드백 창구를 만들지 않는다.** 스토어 리뷰와 이메일로만
받는다(`docs/STORE_SUBMISSION_ANSWERS.md` §2의 '수집 없음' 신고를 지키기 위함).

- **스토어 리뷰·이메일은 오너만 볼 수 있다**(Play Console·메일함). 에이전트는 접근 못 한다.
- 오너가 리뷰·문의를 붙여넣으면 `voice`가 분류·우선순위화해 주간 보고에 싣는다.
- **행동 데이터는 우리가 모으지 않는다**(2026-09-22 결정, §4 참조). 그래서 말이 없으면
  **정말로 모른다** — 리뷰 0건을 문제 0건으로 읽지 않는다. 대신 출시 후 Play Console의
  설치·유지율을 오너가 주간 보고에 기입해 행동의 자리를 채운다.

| 보는 것 | 방법 |

| 백그라운드 작업·에이전트 | `/tasks` |
| 자동 정기 작업 | PC 작업 스케줄러 — `naechaget-daily-report`(매일 12:00) · `naechaget-home-tunnel`(상시) · `NaechaGet-PhotoClassify`(주간) |

| 운영 실적 요약 | `docs/daily-reports/` |

별도 모니터링 서버를 세우지 않는 이유: 위 다섯으로 **이미 보이고**, 서버를 하나 더
운영하는 비용이 이 규모에 맞지 않는다. 부족해지면 그때 다시 판단한다.

## 7. 불변 원칙 (어느 부서도 못 넘는 선)

1. **데이터 신뢰성이 1순위.** 없는 것을 지어내지 않고, 모르면 "모른다"고 말한다.
2. **시세 출처명(중고차 플랫폼)·매물 링크는 어떤 경우에도 공개 금지.** 출시가 출처명도
   권리자 조건에 따라 비공개(`tests/test_exposure.py`가 강제).
3. **외부 수집은 지연·상한·차단중단**을 지킨다(CLAUDE.md C.4). 완화는 오너 승인 사항.
4. **화면을 고치면 디자인 검수**(6폭 측정 → 육안 → 전문가 검수 → 재측정).
5. **경매는 취소가 안 된다.** 잘못된 추천은 고객의 실제 금전 손해다.
