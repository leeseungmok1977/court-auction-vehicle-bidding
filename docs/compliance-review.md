# 준법·리스크 검토 (compliance-officer)

> 코드가 아닌 리스크 검토·로드맵. **최종 법적 판단은 사람(변호사)에게 위임.** 여기서 "합법"을 단정하지 않는다.
> billing 활성화·유료 시세 노출은 아래 완화방안 충족 전까지 **불가**.

## 2. 대체 시세 소스 로드맵 (엔카 의존 탈피)
1. **(a) 자체 축적 낙찰가 DB** — 우리가 합법적으로 모은 실제 낙찰가로 예측(백테스트 기반). **가장 안전**, 데이터 축적할수록 정확. → 우선 투자.
2. **(b) 공식 제휴/공개 API** — 엔카·케이카·KB차차차 제휴 또는 공개 시세 API 조사.
3. **(c) 공공데이터** — 국토부 자동차 이전등록/자동차관리정보 등 활용 가능성 조사.

## 3. 개인정보(회원 DB) 체크리스트
- [ ] 최소수집(이메일 등), 수집·이용 동의, 목적 명시
- [ ] 비밀번호 해시(bcrypt 등)·전송 암호화(HTTPS)
- [ ] 보관기간·파기 정책, 접근통제
- [ ] 개인정보처리방침 게시

## 4. 전자상거래 표시의무 체크리스트
- [ ] 사업자정보(상호·대표·사업자번호·주소·연락처)
- [ ] 이용약관·개인정보처리방침·환불규정
- [ ] 결제 전 과금 조건 고지, 청약철회 안내

## 5. 결론(현재)
- **감정평가서 원본 연결(뷰어)**: 저장·재배포 없이 공식 원본을 여는 현 방식은 리스크 낮음 → 진행 가능.
- **엔카/케이카 시세의 유료 노출**: §2 대체 소스 전환 또는 제휴 확인 전까지 **보류**. 무료 검증 도구로는 현 방식 유지 가능(사용자 승인 하).
- **개인 식별정보**: 유료화 전 마스킹·최소화 검토.
- 결제·회원 활성화: §3·§4 충족 + 위 시세 이슈 해소 후, 사람(변호사) 최종 확인 하에.
- **보배드림 신차가격표**: §6 참조 — **조건부 가능**(내부 파생값 한정). 유료 리포트에 출처와 함께 노출하는 것은 §6.7 조건 (A) 또는 (B) 충족 전 **불가**.

## 6. 보배드림 '신차가격표' 활용 검토 (2026-09-11 추가)

> 이 절도 §1~§5와 동일하게 **리스크 식별·로드맵**이며 법적 판단이 아니다. 인용한 조문·판례 번호는 검토자 기억에 근거하므로 **변호사가 원문으로 재확인**한다.

- 수집: 서버가 물건의 제조사·모델·연식에 맞는 페이지만 소량·저속으로 읽음. 요청 간 5초, 모델당 약 30요청, 일일 상한 300, 모델 단위 1회 캐시.

### 6.2 엔카 사례와의 일관성 판단

| 비교 항목 | SK엔카(기존 결론) | 보배드림 신차가격표(제안) |
|---|---|---|
| robots.txt | 전면 `Disallow: /` | 없음(404) — **엔카보다 유리** |
| 약관상 금지 | (검토 당시 미상) | **영리행위·정보 복제·타인 제공 명시 금지** — 엔카와 실질 동등한 거부 의사 |
| 데이터 성격 | 매물 시세(보배드림 대비 변동성 큼, 원자료 자체가 상품) | 제조사 공표 사실(출시가)의 편집·DB — 원 사실은 공공연히 알려진 정보 |
| 우리 저장물 | 중앙값·표본수·분포(원자료 통계) | min/max/등급수/출시일 구간 |
| 공개 노출 | **관리자 전용, 공개 화면 비노출**(M01) | **유료 리포트에 출처와 함께 노출 예정** — **엔카보다 노출 수위가 높음** |
| 실제 차단 | 2026-09 서버 IP 차단됨 | 없음(아직) |

결론: 저작권 관점은 보배드림이 엔카보다 안전하지만, 약관 금지가 명시적이고 노출 수위는 더 높다. **일관성을 지키려면 초기에는 엔카와 같은 격리 원칙(파생값 계산에만 사용, '보배드림' 문자열과 범위 자체는 관리자 화면 한정)을 적용하고, 공개·유료 노출은 6.7 조건 충족 후 열어야 한다.** 단, 이용하는 이상 출처 표기는 옳다 — 숨기고 쓰는 것보다 밝히고 쓰는 편이 '공정한 관행' 판단에 유리하다. 문제는 표기 여부가 아니라 **허락 없는 공개 재제공** 자체다.

### 6.3 저작권·DB권 관점 정리 (검토 항목 1)

- **사실 정보**: 가격·등급명·출시일은 저작물이 아니다. 보배드림이 이 사실의 원천(제조사)도 아니다. → 개별 사실 인용 자체의 저작권 리스크는 **낮음**.
- **편집물**: 보호 대상은 선택·배열의 창작성뿐이며, 우리는 배열을 복제하지 않는다. → **낮음~중간**(창작성 인정 여부는 다툼 여지, 단정 불가).
- **데이터베이스제작자 권리**: 가장 실질적인 쟁점. '상당한 부분' 기준은 **양적(전체 대비 비율)과 질적(투자의 핵심 부분인가)** 모두로 판단하며, 여기에 **제93조 제2항의 반복적·체계적 추출 간주 조항**이 붙는다. 모델당 집계값은 양적으로 미미하나, 시스템이 물건마다 모델을 순회하고 캐시가 누적되면 "반복적·체계적"이라는 문언에 걸린다. 우리 쪽 방어는 (i) 저장물이 소재의 복제가 아닌 2차 통계라는 점, (ii) 누적 범위가 물건 발생에 따른 필요 한도라는 점, (iii) 통상적 이용(사용자가 가격표를 열람하는 것)과 충돌하지 않고 오히려 링크로 환원한다는 점. **이 방어가 통하는지는 변호사 판단 사항이며, 이 검토는 "낮다고 볼 여지가 있다"까지만 말한다.**
- **공정이용(제35조의5)**: 비영리가 아니고 유료 리포트에 쓰므로 목적 요소는 불리, 이용 분량은 유리, 시장 대체성은 낮음. 보조 근거로만 활용.

### 6.5 리스크를 낮추는 운용 조건 (검토 항목 2 — 체크리스트)

**요청 통제**
- [ ] 요청 간 5초 이상, 동시 연결 1, 재시도 최대 2회·간격 30초(C.4 그대로).
- [ ] 모델당 30요청 이하, 일일 300요청 이하를 **코드 하드캡**으로 강제(설정으로 늘릴 수 없게).
- [ ] 트리거는 **물건 발생 시 on-demand**만. 전체 제조사·모델 카탈로그를 선제 순회하는 배치 금지.
- [ ] 캐시는 모델·연식 단위 **영구 1회**(출시가 불변). 재수집은 신규 연식이 등장했을 때만.
- [ ] 누적 커버리지 상한(예: 모델 500개). 도달 시 자동 정지 + 재검토.
- [ ] User-Agent에 서비스명·연락 이메일 기재. 브라우저 위장·프록시·IP 변경 금지.
- [ ] 회원 로그인·쿠키·세션 미사용.
- [ ] 피크 시간대(예: 09~18시) 회피, 야간 저속 실행.

**저장·표시**
- [ ] 저장 필드: 출시가 min·max, 등급 수, 출시일 구간, 수집일, 조회 URL. **등급명·개별 가격·HTML·이미지·문구는 저장 금지(로그 포함).**
- [ ] 표시 문구(초안): "출시가 범위(참고): 3,294~4,5xx만원 · 등급 n개 · 출처: 보배드림 신차가격표(YYYY-MM 조회) · 본 서비스는 보배드림과 제휴관계가 없으며, 위 수치는 참고용이고 정확성을 보증하지 않습니다." + 해당 가격표 페이지 링크(트래픽 환원).

- [ ] 매칭 신뢰도 낮은 물건은 미표시(R9).

**중단·옵트아웃**
- [ ] 자동 중단 조건: 403/429/407, CAPTCHA, 비정상 응답 3회 연속, robots.txt에 `Disallow` 등장, 약관 개정으로 자동수집 명시 금지.

**기록**

- **localStorage(favs·notes·large·scroll·splash)**: Google 기준은 *"'Collect' means transmitting data from your app **off a user's device**"*이고 면제 (a)가 **기기를 떠나지 않는 데이터**다(2026-09-22 확인, `reports/2026-09-22-compliance-출시전-신고정합성.md` G2·G3). 기기를 떠나지 않으므로 **수집 아님**. 신고 영향 없음.
- **쿠키 `last_list`**: localStorage와 달리 **매 요청 서버로 전송된다.** 그럼에도 수집으로 보기 어렵다고 판단하는 근거는 셋이다 — ① 내용이 *우리가 방금 내려준 우리 자신의 목록 URL*이고 ② 서버는 '이전 목록' 링크를 만드는 데만 쓰고 저장하지 않으며(`app.py:761-763`, 내부 상대경로만 허용) ③ 난수 ID·세션 ID 같은 **식별자가 아니다**(Google의 'Device or other IDs' 예시는 IMEI·MAC·Widevine·Firebase ID·광고 ID). **이것은 해석이며 단정이 아니다.**
  ⚠ **뒤집히는 조건**: 이 쿠키에 임의 ID(세션·방문자 식별자)를 넣는 순간 '기기 또는 기타 ID' 판정으로 넘어간다. 쿠키에 식별자를 추가하는 변경은 **오너 승인 사항**(ORG §3)으로 취급해야 한다.

### 8.3 항목 3 — `/terms` 404: 출시 시점에 이용약관이 없어도 되는가

**판단(법적 단정 아님)**

- **Play 심사**: 필수는 **개인정보처리방침**이다. 이용약관은 **UGC를 만들거나 업로드하는 앱**에서 수락 절차를 요구하는 맥락으로 서술된다([앱 준비](https://support.google.com/googleplay/android-developer/answer/9859455?hl=ko), [개발자 정책](https://support.google.com/googleplay/android-developer/answer/14906471?hl=ko)). 이 앱은 댓글·게시판·업로드가 없다(콘텐츠 등급 답안 §3과 일치). → **Play 관점에서 출시 차단 요인 아님.**
- **전자상거래법 제10조**(사이버몰 운영자 표시의무: 상호·대표자 성명·주소·전화·이메일·사업자등록번호·**이용약관**·호스팅사업자 상호를 초기화면에 표시)는 *"전자상거래를 하는 사이버몰의 운영자"*에 걸린다([조문 해설](https://easylaw.go.kr/CSP/CnpClsMain.laf?popMenu=ov&csmSeq=25&ccfNo=3&cciNo=1&cnpClsNo=1)). 현재는 **판매·결제·광고가 전혀 없어** 적용 대상으로 보기 어렵다는 것이 이 검토의 잠정 판단이다. **유료 전환 시에는 §4 체크리스트 전부가 한꺼번에 걸린다.**
- **실질적 손해**: 약관이 없으면 ① 서비스 이용조건·면책 ② **§6.5/§6.6의 데이터 제공 중단(권리자 요청 시)** ③ 분쟁해결·준거법을 계약으로 못 박을 자리가 없다. 특히 ②는 유료 이용자에게 사전 고지해 둬야 환불 분쟁을 예방하는 항목이다(§6.6-4).

**판정: 출시 차단 아님. 출시 후 정비 1순위.** 심각도 **중간**(무료 v1) → **높음**(유료 전환 시).

1. **창구 단일화**: 수신은 `koreanplus@gmail.com`(방침 §8에 이미 공개돼 있다). 접수 즉시 대표에게 보고한다.
2. **서면 요청 수령 시 24시간 내**(§6.5 옵트아웃 절차와 같은 기준): ① 해당 물건 사진 비공개 → ② og:image를 브랜드 이미지로 대체 → ③ **외부 캐시 무효화 요청**(카카오·페이스북 공유 디버거, Search Console 삭제 도구) → ④ 처리 결과 회신.

4. **기록**: 요청일·요청자·범위·조치 시각을 이 절 아래에 추기한다. 분쟁에서 '성실히 대응했다'는 사실이 그 자체로 방어 자료다.
5. **트리거 감시**: 법령 개정이나 Play 정책 변경으로 마스킹이 **의무**가 되면 그때가 §7이 정한 '되돌리는 경우 2'다 — 그 경우에만 대표에게 올린다.

### 8.7 점검 중 새로 발견 — 스토어 등록정보 수치가 라이브와 다르다

**확인된 사실 (2026-09-23 라이브 `/accuracy` 직접 조회 vs `docs/STORE_LISTING.md`)**

| 값 | 등록정보 문서(`STORE_LISTING.md:20·37-40`) | **라이브 `/accuracy`** |
|---|---|---|
| 평균 오차 | ±9.3% (짧은 설명·긴 설명 **2곳**) | **±9.5%** |
| 검증 표본 | 249건 | **275건** |
| ±20% 이내 적중 | 95% | **94%** |

(라이브 부가 수치: ±10% 이내 61%, 중앙값 낙찰가율 74%, 낙찰가 중앙 절반이 시세의 62~85%.)

**왜 문제인가**
- 2026-09-22 보고서 5-1이 정확히 이 항목을 "출시 신청 직전 대조하라"고 예고했고, **실제로 어긋났다.** 검증 표본이 매일 쌓이므로 **기준 시점 없이 숫자만 박으면 반드시 낡는다.**
- Play는 등록정보·스크린샷 등 모든 메타데이터가 앱을 정확히 반영할 것을 요구하고, 허위표시를 삭제·정지 사유로 든다([Misrepresentation](https://support.google.com/googleplay/android-developer/answer/9888689), [개발자 정책](https://support.google.com/googleplay/android-developer/answer/14906471?hl=ko)).
- 국내법으로는 **표시광고법 제3조**(거짓·과장 광고)와 **제5조**(사업자의 실증책임 — 공정위 요청 시 15일 내 자료 제출)가 걸린다([법령](https://www.law.go.kr/LSW/lsInfoP.do?lsId=002011&ancYnChk=0), [해설](https://www.consumer.go.kr/user/bbs/consumer/380/940/bbsDataView/2813.do)). 다행히 우리는 **실증자료를 갖고 있다**(`/accuracy`의 자기제외 검증) — 문제는 자료가 아니라 **숫자가 낡았다는 것**이다.

**심각도: 중간. 출시 전 처리 권고.**
완화: 출시 신청 직전 라이브 값으로 교체하고 **"2026년 9월 기준"처럼 기준 시점을 병기**한다. 등록정보 텍스트는 콘솔에서 즉시 수정되며 재빌드가 필요 없다.
**미확인**: Play Console에 **실제로 저장돼 있는** 문구. 나는 콘솔을 보지 못했고 저장소 문서와 대조한 것이다. 콘솔 값이 이미 갱신돼 있으면 이 항목은 자동 해소된다.

**함께 발견(낮음)**: `STORE_LISTING.md:63` "가입·로그인·결제·광고 없이 바로 이용합니다. **개인정보를 수집하지 않습니다.**" 는 `/privacy` §1이 접속 로그·쿠키를 수집 항목으로 적어 둔 것과 **문자 그대로는 충돌한다.** Play 신고 기준으로는 '수집 없음'이 성립하지만(8.1), 이용자에게는 두 문장이 서로 다른 말로 읽힌다. 완화: "개인정보를 수집하지 않습니다(계정·결제·광고 없음 — 서버 운영 로그만 일정 기간 보관)"처럼 한정하면 양쪽이 같은 말이 된다.

### 8.9 한계와 위임

- **Play Console을 보지 못했다.** 콘솔 실제 저장값이 저장소 문서와 다르면 8.7의 대조 전제가 흔들린다.
- **라이브 DB 설정(`adsense_client`)과 서버 nginx 로그 설정을 확인하지 못했다.** 둘 다 '미확인'으로 표기했다.
- 인용한 Google 정책 문언 중 G1~G7은 2026-09-22에 확인된 것을 재사용했고(`reports/2026-09-22-compliance-출시전-신고정합성.md` §1), 이번에 새로 연 것은 이 절에 링크로 달았다. **Google 도움말은 예고 없이 개정된다** — 출시 신청일에 다시 한 번 열어 볼 것.
- **법 해석은 전부 변호사에게 위임한다.** 이 절은 조문·출처를 달아 리스크를 드러낼 뿐, 개인정보 해당 여부·수집 해당 여부·표시광고 실증·약관 필요성 어느 것도 "합법/위법"으로 단정하지 않는다.
