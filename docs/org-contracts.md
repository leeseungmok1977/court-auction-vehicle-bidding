# 인계 계약 — 누가 무엇을 받아 누구에게 넘기는가

> 2026-09-26 오너 지시로 제정. *"회사라면 각각의 조직원들이 유기적으로 움직여야 하는데,
> 그렇지 않다."*
>
> **이 문서는 조직도가 아니라 배선도다.** 부서 편성은 [`ORG.md`](ORG.md) §1이 정하고,
> 여기에는 **일이 흐르는 길**만 둔다. `tools/org_runtime.py`가 §1·§2 표를 읽어 움직이고
> `tools/agent_dashboard.py`가 같은 표를 읽어 화면에 띄운다 — **표를 고치면 둘 다 따라온다.**
> 표에 없는 경로로 넘기려 하면 순환계는 그 인계를 **실행하지 않고 Steward 결재함으로 올린다.**

## 0. 왜 이 문서가 필요했나 — 2026-09-26 실측

대시보드 조직도에서 읽힌 것:

| 증상 | 실측 | 뜻 |
|---|---|---|
| PM 이 뛰지 않는다 | `pm-orchestrator` 2회·3일 전 / `frontend-engineer` 18회·`app-design-expert` 50회 | 배분을 PM 이 아니라 오너·Steward 가 직접 하고 있다 |
| 경보가 반응을 부르지 않는다 | `리듬중단` 3자리가 13일째 | 화면은 알고 있는데 아무도 깨우지 않는다 |
| 인계가 기록되지 않는다 | `reports/` 38건 중 다음 담당을 **기계가 읽을 형식으로** 적은 곳 0건. 산문으로 적은 곳 1건(`bidder-insight-2026-09-26.md` — "`growth`가 검토할 … 문제로 넘긴다") — 그 인계가 실행됐는지 추적할 방법이 없다 | 다음 담당 연결이 Steward 기억 속에만 있다 |
| 종료 조건 없는 왕복 | 디자인 검수 50회 `과부하` | 같은 티켓에서 몇 번째 왕복인지 아무도 세지 않는다 |

원인은 한 줄이다: **Steward 는 오너가 세션을 열 때만 존재한다.** 서브에이전트는 서로 부르지
못하므로(ORG §1) Steward 가 없으면 조직 전체가 정지한다. 그래서 세 가지를 붙였다.

1. **지시서를 파일로 둔다**(`orders/`) — 기억이 아니라 대기열에 일이 쌓인다.
2. **보고서가 다음 담당을 적는다**(`_handoff-protocol.md` 머리말) — 순환계가 그것을 읽어 다음 지시서를 만든다.
3. **당직 Steward 가 정해진 시각에 깨어난다**(작업 스케줄러) — 오너가 없어도 자동 실행 가능한 지시서를 처리한다.

## 2. 부서별 계약

- **받는 일**: 이 자리가 깨어나는 조건. 여기에 없는 일로 부르지 않는다.
- **넘길 수 있는 곳**: 보고서 머리말 `handoff:` 에 적을 수 있는 담당. `steward`(결재함)는 누구나 쓸 수 있다.
- **자동**: `예`면 당직 Steward 가 오너 없이 부른다. `아니오`면 지시서가 쌓이기만 하고 **오너가 연 세션**에서 처리한다.
  코드를 고치는 자리·외부에 요청을 보내는 자리·오너 입력이 필요한 자리는 전부 `아니오`다.
- **리듬(일)**: 이 일수 동안 이 자리에 지시서가 한 건도 없으면 순환계가 정기 지시서를 만든다. `-`는 부를 때만 일한다.
  ★ 정기 지시서는 **일을 지어내라는 뜻이 아니다.** 볼 것이 없으면 `result: done` 한 줄로 닫는다(프로토콜 §3).
- **왕복 상한**: 비우면 §1 기본값.

> 루틴**이 부른다. 이 자리의 리듬이 끊기면 사람을 부를 게 아니라 루틴 인프라를 봐야 한다
> (agent-utilization §4) — 그래서 순환계는 이 경우 에이전트가 아니라 **Steward 결재함**으로 올린다.

## 3. 순환계가 스스로 만드는 지시서

| 계기 | 받는 자리 | 중복 방지 |
|---|---|---|
| 보고서 머리말 `handoff:` | 적힌 담당(계약에 있는 경로만) | 같은 보고서 → 같은 담당은 한 번. **만들지 않는 경우**: 보고서 머리말에 `workflow:` 가 있을 때(다음 단계는 워크플로가 부른다), 또는 보고서가 답한 지시서(`order:`)를 `steward` 가 발행했고 같은 티켓·같은 담당으로 `open`·`doing` 지시서가 이미 있을 때 — 대신 `data/org-bus.jsonl` 에 `handoff.skipped` 한 줄 |
| 보고서 `result: fail`·`blocked` 인데 `handoff:` 없음 | `pm-orchestrator` | 보고서당 한 번. `workflow:` 보고서면 만들지 않고 `result.skipped` 한 줄(반려·재배분은 워크플로가 정한다) |
| 보고서 `result: needs-owner` | `steward` | 보고서당 한 번. `workflow:` 여도 **막지 않는다** — 오너 결정은 결재함에 반드시 올라간다 |
| 왕복 상한 초과 | `steward` | 티켓·담당당 열린 것 한 건 |
| 리듬 감시(agent-utilization §3) `늦음`·`끊김`·`없음` | 담당 칸의 에이전트가 계약상 `자동: 예`면 그 자리, 아니면 `steward` | 산출물당 열린 것 한 건 |
| 백로그 `todo` 인데 지시서가 없는 티켓 | `pm-orchestrator` (묶어서 한 건) | 열린 것 한 건 |
| 정체 기준을 넘긴 열린 지시서 | `pm-orchestrator` (묶어서 한 건) | 열린 것 한 건 |
| §2 리듬(일) 동안 지시서가 없던 자리 | 그 자리 | 리듬 주기당 한 건 |
| **경보**(`reason: alert`) — 일일 리포트(`docs/daily-reports/`)의 같은 신호가 §1 `경보 연속 기준(리포트)` 편 **연속으로** 이상·멈춤(사이의 ❔ 모름은 세지도 끊지도 않는다 — 아래 규칙) | §3.1 받는 자리(표에 없으면 `steward`). **§3.1 티켓이 백로그에서 열려 있으면 만들지 않는다**(이미 누가 맡았다) | 신호·연속 구간당 한 건(키 `alert:<신호>:<구간 첫 날짜>` — 닫거나 취소해도 같은 구간에서는 다시 안 만든다) + 같은 신호의 열린 것 한 건. **구간 첫 날짜는 처음 본 날로 고정한다**(`data/org-state.json` 의 `alert_runs` — 신호별 시작일·지시서 id). ✅ 정상 리포트가 끼기 전까지 같은 구간이다 |
| **예약 작업**(`reason: task`) — `naechaget*` 작업이 '실패' · '다음 실행 없음' · '꺼짐(Disabled)' · '실행된 적 없음 · 예정도 없음' · '미등록'(판정 이름 그대로)인 채 §1 `예약 작업 실패 지속(시간)` 을 넘김 | §3.1 받는 자리(표에 없으면 `steward`). 열린 티켓이 있으면 만들지 않는다 | 작업·고장 구간당 한 건(키 `task:<작업>:<고장 시작>`) + 같은 작업의 열린 것 한 건 |

**경보·예약 작업 지시서를 읽는 규칙** (OPS-3, 오너 승인 2026-09-27)

- **경보는 일일 리포트에서 읽는다** — 운영 서버를 본 것은 그 리포트뿐이다(로컬 DB 로 판정하면 거짓 경보, `web/ops_health.py` 머리 주석).
  **연속을 끊는 것은 `✅` 정상 리포트뿐이다.** 리포트가 없는 날, 공급 표가 없거나 `❔` 인 날(서버를 못 읽음 · 지난 기간)은
  **세지도 끊지도 않는다.** ⚠ 지난 기간은 `--date` 로 다시 만든 리포트만이 아니다 — **14:00 넘어 만든 당일 리포트도**
  공급 절이 `❔ 지난 기간`이다(`daily_ops_report` 의 `supply_live` = 기간 끝 + 2시간. 09-22 리포트가 17:08 에 생성됐다).
  건너뛴 모름은 지시서 목적과 스탠드업 '경보 → 티켓' 줄에 `[사이의 ❔ 모름 N편은 세지 않음]` 으로 적는다.
  주간 작업(토요일 패널 등)의 `— 없음` 은 예정이 없던 날이라 세지도 끊지도 않는다 — 그래서 주간 작업의 '연속 2편'은 **연속 두 회차**다.
  - 지연: 경보 뒤에 모름이 끼면 **그 모름 편수만큼** 지시서가 늦는다(두 번째 경보 리포트가 나올 때 만든다). 끊지 않으므로 늦은 리포트가 반복돼도 늦음이 쌓이지 않는다.
    (2026-09-27 전 규칙은 모름이 끊었다. 한 번 끊기면 2일 늦었고, 늦은 리포트가 하루걸러 끼면 🛑 8일이 **지시서 0건·경고 0건**이었다 — QA-OPS3-3.)
  - 대가: 경보·모름·경보면 가운데 날이 실제로는 정상이었어도 한 구간으로 본다. 결재함에 한 장 더 쌓이는 쪽을 택했다(경보가 조용히 사라지는 쪽보다 낫다).
  - 마지막 경보가 조회 창(`ALERT_LOOKBACK_DAYS` 21일)보다 오래됐고 그 사이 아무것도 몰랐으면 구간을 버린다 — 3주 넘게 모른 뒤의 경보는 새 구간이다.
- **형식이 어긋난 리포트는 경고로 드러낸다**(QA-OPS3-2). 공급·정기 작업 표의 열 이름이 다르거나, 읽힌 행이 0이거나, 모르는 상태 표시가 있거나,
  공급 절 머리글이 `## 공급 상태` 가 아니거나, 공급 절에 표도 '지난 기간'·'확인 불가' 문장도 없으면(공급 절이 생긴 2026-09-24 이후 리포트)
  순환계가 **파일명을 붙여** 스탠드업 '읽지 못한 것'에, 주간 보고가 운영 절 머리에 적는다. 경보 0건이 '이상 없음'인지 '못 읽음'인지 가르기 위해서다.
- **'중지(의도)'는 경보가 아니다.** 케이카처럼 오너 결정으로 끈 신호는 `✅ 정상 · 중지(의도)` 로 적히므로 지시서가 생기지 않는다.
- **예약 작업 판정은 사내 대시보드 정기 작업 표와 같은 목록·같은 규칙이다**(`agent_dashboard.read_schedule`, defaccc).
  한 번도 안 돌았어도 다음 실행이 잡혀 있으면 '아직 때가 안 됨'이라 고장이 아니다. 목록을 못 읽은 것은 '없음'이 아니라 '못 읽음'이라 지시서를 만들지 않고 경고로만 남긴다.
  돌지도 않고 다음 실행도 없으면('실행된 적 없음 · 예정도 없음')과 결과가 0 이 아닌 실패는 **대시보드도 고장으로 칠한다**(터널 09-16 0xC0000005 도 대시보드에서 이미 고장이다).
  대시보드에 없는 규칙은 **둘**이다(대시보드는 결과가 0 이면 정상으로 칠한다): ⓐ 결과 0 인데 **다음 실행이 없으면** '다음 실행 없음'(다시는 안 돈다),
  ⓑ **꺼진 작업**(Disabled)은 '꺼짐(Disabled)'. 일부러 끈 작업이면 §3.1 받는 자리를 `-` 로 바꾼다 — 그대로 두면 24시간 뒤 결재함에 올라간다.
  - 판정은 **고장 상태가 24시간 이어졌는가**다. 결과 0 인 채 실행을 건너뛰었고 다음 실행은 잡혀 있는 작업(따라잡지 않는 매일 작업)은 고장으로 보지 않는다 — QA-OPS3-4, Steward 결정 대기.
- **당직은 이 두 사유의 지시서를 부르지 않는다.** 고치려면 코드·서버·관리자 권한이 필요한데 당직에는 없다(§4).
  받는 자리를 자동 자리로 적어도 `tools/org_runtime.py` 가 디스패치에서 뺀다(`NO_DISPATCH_REASONS`). 당직은 스탠드업의
  결재함·'경보 → 티켓' 절에 적기만 하고, Steward 가 **당일** 티켓을 만들거나 기존 티켓에 붙이거나 '의도된 상태'로 판정해 닫는다.
- 일일 리포트는 같은 표를 읽어 이상·멈춤 줄마다 티켓 ID 를 붙이고, 없으면 **❗ 티켓 없음**을 적는다. 주간 보고의 '운영·공급' 절도 같은 표를 쓴다.

### 3.1 경보 신호 → 담당 · 티켓

- **신호**: 공급 신호는 `web/ops_health.py` 의 신호 이름(일일 리포트 `## 공급 상태` 표의 첫 칸), 정기 작업은 일일 리포트 `## 정기 작업` 표의 작업 이름, 예약 작업은 작업 스케줄러의 작업 이름이다. **글자까지 같아야** 맞는다.
- **받는 자리** `-` 는 이 신호로는 지시서를 만들지 않는다는 뜻이다(같은 원인을 다른 신호가 본다 — 두 번 세면 결재함에 같은 일이 두 장 쌓인다). 티켓 칸은 그래도 리포트 표기에 쓴다.
- **티켓**: 그 신호의 경보를 **지금 맡고 있는** 백로그 티켓. 티켓이 닫혔는데 경보가 계속되면 지시서가 생긴다. 다른 주제의 티켓을 적지 않는다 — 진짜 고장이 그 티켓 뒤에 숨는다.
- 이 표를 고치면 순환계·일일 리포트·주간 보고가 **함께 따라온다.** 티켓이 바뀌면 여기 한 곳만 고친다.

## 4. 당직 Steward 가 하지 않는 것

오너 승인 항목(ORG §3)은 **도구 권한으로 막는다** — 헤드리스 실행에는 허용 목록 밖 도구가 전부
거부된다. 커밋·푸시·ssh·배포·설정 변경·코드 편집은 허용 목록에 없다.
당직은 오너 승인이 필요한 결론에 닿으면 보고서를 `result: needs-owner`로 닫고 멈춘다.
**경보·예약 작업 지시서(`reason: alert`·`task`, §3)는 부르지 않는다** — 디스패치 계획에서 빠지고
(`NO_DISPATCH_REASONS`), 손으로 불러도 거부된다. 당직은 스탠드업 결재함·'경보 → 티켓' 절에 적기만 한다.

### 실측 — 이 막음이 서브에이전트까지 닿는가 (2026-09-26)

첫 당직 실행(`compliance-officer`, 저장소 복사본)이 스스로 이 절의 빈틈을 짚었다: *"허용·금지 목록은
최상위 `claude -p`에만 넘어가는데, 당직이 `Agent`로 위임한 서브에이전트에도 적용되는지는 미검증이다."*
맞는 지적이라 **도구 계층에서 직접 쟀다.** 조건: Claude Code 2.1.283 · Linux · 저장소 복사본 ·
`tools/org_runtime.py` 의 `_claude_cmd()` 그대로 · 당직이 `general-purpose` 서브에이전트에게 쓰기 두 건을 시킴.

| 서브에이전트의 쓰기 | 도구가 돌려준 결과(원문) |
|---|---|
| `src/_probe_sub.txt` | `File is in a directory that is denied by your permission settings.` — 파일 없음 확인 |
| `reports/_probe_sub.txt` | `File created successfully` — 파일 있음 확인 |

→ **최상위의 허용·금지 목록이 위임된 서브에이전트의 도구 호출에도 적용된다.** 에이전트 정의의 `tools:`
(예: `design-critic` 의 경로 없는 `Write`)는 이 목록을 넓히지 못한다.
⚠ 같은 날 `design-critic` 으로 먼저 쟀을 때는 서브에이전트가 **역할 밖 지시라며 스스로 거부**해서
도구 계층을 관찰하지 못했다. 그 결과를 "도구가 막았다"로 적지 않았다 — 막은 것은 도구가 아니라 판단이었다.
Claude Code 버전이 오르면 이 표를 다시 잰다.
