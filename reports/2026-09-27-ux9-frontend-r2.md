## 2. 무엇을 바꿨나 — 앵커로 가리킨다

수정한 파일은 `web/templates/vehicles.html` 하나다.
- `base.html`·`tailwind_input.css`는 건드리지 않았다.
- `npm run build:css` 전후 `app.css` md5는 `f901bb86` 그대로다. 쓴 클래스는 모두 이미 있던 것이다.

**⑴ 스켈레톤 IIFE**
- 앵커: `var res=document.getElementById('listResults')`부터 그 뒤 줄 첫머리의 `})();`까지.
- R1 처방: 이동마다 오는 `navigate` 이벤트의 `signal`이 abort되면, 한 틱 뒤 그 이동이 여전히 마지막 이동일 때만 `undo()`를 부른다.
  ```js
  var nv=window.navigation, last=null;
  if(nv && nv.addEventListener) nv.addEventListener('navigate', function(e){ var me=last=e;
    if(e.signal) e.signal.addEventListener('abort', function(){ setTimeout(function(){ if(last===me) undo(); }, 0); }); });
  ```
- 한 틱 미루는 이유: 연타나 커밋 전 뒤로가기처럼 다른 이동이 이어받아 abort된 경우에는 같은 태스크 안에서 새 navigate 이벤트가 온다. 그런 경우까지 되돌리면 목록이 번쩍 다시 나온다.
- C1: 주석의 `(측정은 reports/2026-09-27-ux9-frontend.md)`를 지우고 수치를 직접 적었다. pageshow만 쓴 방식은 15/15회 스켈레톤 2~4프레임·최대 334ms에 스크롤이 313/377로 틀렸고, 지금 방식은 10/15회 1프레임·최대 148ms에 스크롤이 정확하다. 원자료 screenshots/ux9/firstpaint-*.txt와 대조했다. R2의 원인도 한 줄 덧붙였다.

**⑵ [적용] 변경 표시 IIFE**
- 앵커: `function mark(on)`부터 그 뒤 줄 첫머리의 `})();`까지.
- 기준값: `var base=ser()`(로드 시점의 폼 값)를 **복제한 폼에 `reset()`을 건 직렬화**로 바꿨다. `reset()`은 각 칸을 HTML 기본값, 즉 서버가 그린 값으로 돌린다.
- pageshow: 무조건 `mark(false)`를 하던 것을 `sync`(기준과 다시 비교)로 바꿨다.
- 떠날 때: 제출하면 `sent` 플래그를 세우고, `pagehide`에서 `sent`일 때만 `f.reset()` 후 `mark(false)`를 한다. 폼 상태는 bfcache가 얼릴 때도, Chrome이 저장할 때도 pagehide **뒤에** 기록된다(Chrome 153 실측). 그래서 bfcache 복원과 새 로드 모두 되돌린 값으로 돌아온다.
- [적용] 없이 바꾼 값은 남긴다. 대신 돌아오면 변경 표시를 켠다(예전에는 껐다).

**⑶ 페이지 이동 줄**
- 앵커: `{% if total_pages > 1 %}` 뒤의 첫 `<nav`.
- `flex items-center gap-1`을 `flex flex-wrap items-center gap-x-1 gap-y-2`로 바꿨다.
- '‹ 이전'·'다음 ›'는 링크와 비활성 span 모두에 `whitespace-nowrap`을 붙였다.
- Jinja 로직·href·필터는 바꾸지 않았다. 스타일 클래스와 `{# #}` 주석만 바꿨다.

**테스트**

## 4. 반영하지 않은 것과 이유

**R2 — 복원 직후 1프레임**
- 확인된 사실: pagehide(capture) 시점에 DOM은 이미 목록이다. 그런데도 첫 프레임에 스켈레톤이 보인다. 즉 페이지가 새로 그린 것이 아니라, **얼기 전에 마지막으로 그린 화면을 브라우저가 한 번 보여 주는 것**이다. r1의 변형 실험(firstpaint-variants)과 QA 측정(CPU 스로틀 시 0회)이 이와 맞는다.
- 페이지 쪽 수단은 '스켈레톤을 그리기 전에 떠나게 하기', 즉 표시를 늦추는 것 하나뿐이다.
- 그런데 이동 커밋까지 걸리는 시간이 로컬 기준 `/vehicles?…page=2` 응답 0.36초다(첫 요청은 0.87초, 이 PC의 스크래치 서버에서 curl로 잰 값). base.html 주석에 적힌 운영 모바일 실측은 **홈** 전환의 서버 응답 0.5초다.
- 이보다 짧게 늦추면 현장에서는 결국 그려지고, 이보다 길게 늦추면 느린 망에서 스켈레톤의 가치가 줄어든다(추정).
- 그래서 QA 말대로 디자인 판단이 먼저다. 코드는 바꾸지 않았다.
- 실기기에서 볼 점(추정, 미검증): 안드로이드의 예측형 뒤로가기 제스처가 떠날 때 찍은 화면을 쓰면, 1프레임보다 오래 보일 수 있다. C2 확인 때 함께 봐 주기 바란다.

**페이지 버튼 히트영역 34px**
- 디자인이 범위 밖으로 따로 판단하자고 했고, 이번 지시의 번호 항목에도 없다.
- 높이를 올리면 줄바꿈과 겹쳐 푸터가 더 커진다. 그래서 줄바꿈과 함께 디자인이 판단하는 것이 맞다.

**좁은 폭의 compact 페이저**
- 예: '‹ 이전 · 5/110 · 다음 ›' 형태, 또는 ±2를 ±1로 줄이기.
- 번호 링크를 줄이는 것은 UX 변경이고 테스트('2'를 누르는 경로)도 흔든다. 이번에는 '잘리지 않음'만 보장했다.

**QA-3(큰글씨 320 헤더 검색 아이콘 7px)**
