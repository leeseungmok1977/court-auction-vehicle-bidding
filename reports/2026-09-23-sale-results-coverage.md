# [insight] 2026-09-23 sale_results 커버리지 — 257건 중 138건만 담긴 이유

- 지시서: 2026-09-23-13 / insight
- 대상: web/service.py(backfill_sale_results·record_sale_result 호출부·no_market_reason·requery_missing_market), web/db.py(record_sale_result·스키마), data/auction.db(읽기 전용)
- 방법: sqlite3 읽기 전용 연결(mode=ro) + 코드 정적 분석. DB 쓰기 없음, 외부요청 없음, pytest 미실행, 로컬 서버 미기동.

---

## [분석 요청] 받은 지시 요약

sale_results(140행, 테스트오염 W1·DONE1 제외 138행)가 낙찰+winning_price 보유 물건(257건)의 절반만
담고 있다. "138+2=140이라 정상 백필"이라는 이전 추정은 257과 안 맞으므로 성립하지 않는다. backfill_sale_results·
record_sale_result의 정확한 포함/배제 조건을 코드로 특정하고, 257에서 138을 재현하고, 안 맞으면 잔차를 밝히고,
빠진 물건의 공통점·recorded_at 의미·2026-08 낙찰 실적 창 영향을 판정한다.

## [데이터 출처·기간·조건]

- data/auction.db 2026-09-23 스냅샷, 읽기 전용(mode=ro) 연결.
- "257"·"138"은 Steward가 제시한 원문 그대로 재확인.
- sale_results.id는 court_code|case_no|item_no PK — ON CONFLICT DO UPDATE(전 컬럼 포함 recorded_at)로 upsert.
  즉 recorded_at은 마지막 쓰기 성공 시각이지 생성 시각이 아니다(web/db.py:901-914).
- 봇/폴링/관리자 접속 개념은 해당 없음(서버 로그가 아니라 DB·코드 직접 조회).

## [확인된 사실]

### 1. 포함 조건 — 코드로 특정

`backfill_sale_results()`(`web/service.py:3736-3743`)는 `db.list_vehicles(result="낙찰")`를 순회하며
**`v.get("winning_price") and v.get("median_price")`** 를 만족하는 것만 `record_sale_result()`로 쓴다.
`record_sale_result()`(`web/db.py:901-904`) 자체도 동일 조건(id·winning_price·median_price 셋 다 truthy)을
다시 검사해 아니면 무행동(no-op)으로 반환한다. **`_result_anomaly()`는 이 두 함수 어디에도 걸리지 않는다** —
docstring(`web/service.py:339` "이상 낙찰은…모델 학습에서 제외한다")과 달리, 배제는 `backtest_stats()`가
학습 표본을 고를 때(3133·3137행)만 적용되고, **저장 자체는 막지 않는다.** (참고 — 결과검증 upsert 경로
`web/service.py:2133-2138`은 `_result_anomaly`로 저장을 막지만, 이건 대법원 결과 재조회 시점의 별도 경로다.)

**결론: 매칭 시세(median_price)가 없으면 무조건 빠진다. 이것이 유일한 필터다.**

### 2. 257 → 138 재현

| 구분 | 건수 |
|---|---:|
| vehicles: 낙찰 + winning_price 보유 (Steward 원문) | 257 |
| 〃 + 현재 median_price도 보유 | 134 |
| 〃 median_price NULL (현재) | 123 |
| sale_results 비테스트 실질 | 138 |
| sale_results 중 recorded_at='2026-09-23 15:19:18'(오늘 백필 재실행분) | 134 |
| sale_results 중 recorded_at='2026-09-08 22:41'(정체된 4건) | 4 |
| sale_results 중 테스트오염(W1·DONE1) | 2 |

134 + 4 = **138** — sale_results 실질 행수와 정확히 일치. 재현 성공.

정체된 4건을 확인하니 **전부 현재 vehicles.median_price가 NULL**이다(그래서 오늘 재백필에서 갱신 대상이
못 됐다 — 조건 미충족). 이 중 2건(무쏘 EV, 코나)은 winning_price도 여전히 있어 "257" 모집단에 남아 있고,
2건(스타렉스류, 미상 1건)은 winning_price까지 NULL로 바뀌어 있어 지금은 "257" 모집단에서 아예 빠졌다
(auction_result는 '낙찰'로 남아 있는데 winning_price만 사라진 상태 — 원인 미검증, [한계] 참조).

즉 257건 중 sale_results가 실제로 대변하는 것은 134+2=**136건**이고, **121건이 현재도 빠져 있다**
(257-136=121. Steward가 산술로 추정한 "119"와는 2건 차이 — 그 2건이 바로 위 "winning_price가 나중에
사라진 2건"이다. 산술 추정 119는 이 반전을 못 잡아 틀렸다).

### 3. 빠진 121건의 공통점

**100%(121/121)가 median_price NULL** — 포함 조건 1개와 정확히 일치. 이걸 세 갈래로 더 쪼갰다
(no_market_reason() 재현 + match_label 확인):

| 갈래 | 건수 | 비중 | 성격 |
|---|---:|---:|---|
| A. no_market_reason() 키워드 적중(건설기계·특장) | 28 | 23% | 설계된 배제 — NEWCAR_SKIP_WORDS/NO_MARKET_HEAVY_WORDS(덤프트럭·굴착기·지게차·크레인·믹서 등)에 코드·주석으로 명문화 |
| B. match_label='동급 표본 없음'(검색은 됐으나 0표본) | 44 | 36% | A와 사실상 같은 사유(경상용차: 포터·봉고·다마스·각종 톤수 암롤트럭/음식물수거차/활어운반차 등)인데 키워드 목록이 이들을 못 잡아 A로 분류되지 못한 경계 사례 |
| C. match_label=None(시세 분석 자체가 안 됨) | 49 | 40% | 진짜 설명 안 되는 잔차 — 아래 4번 참조 |

C(49건) 내부:
- 18건은 maker·model이 둘 다 공백 — 수집 시점 파싱 실패(차종을 모르니 시세 검색 자체가 불가능했던 것으로 추정, 미검증).
- **31건은 maker·model이 멀쩡히 있고, 그중 다수가 매칭이 실패할 이유가 없어 보이는 흔한 모델**이다:
  쏘렌토·스포티지·스파크 1.0·카니발·XM3·K7 하이브리드·레이·G80·토레스(3건)·닷지램1500·MINI Cooper SD·
  BMW 730d·Mercedes E300/S350L·VW Tiguan·랜드로버 레인지로버(스포츠)·포르쉐 마칸S 등.
  이 31건 전부 sample_count가 0 또는 None이다.

시점 패턴(위 C 49건 대부분 포함, collected_at 기준): **2026-08-17~18 하루~이틀 사이에 집중 수집**됐다
(49건 중 24건이 08-18, 다수가 새벽 01시대 몇 분 간격). requery_missing_market()의 코드 주석
(web/service.py:4875-4879)은 "물건은 수집 시점에 한 번만 시세를 조회했고, 실패(0건)는 영구였다.
09-10 매핑 개선(법인명·영문·브랜드 접두)도 09-13 계층 수정(렉스턴·제네시스 DH·미니·CLS·수입 한글 음차)도
기존 0건 물건에는 한 번도 적용되지 않았다"고 명시한다 — MINI Cooper SD·Mercedes 계열이 정확히 이 09-13
수정 대상 카테고리와 겹친다. **08-17/18 수집분이 그 이전 매핑 버그로 0표본이 됐을 가능성이 있으나,
이 리포트에서 당시 매핑 코드를 직접 비교하지는 않았다 — [해석·추정]으로만 적는다.**

### 4. 왜 121건이 영구히 안 고쳐지는가 — 구조적 원인 확인

requery_missing_market()(web/service.py:4886-4890)은 0표본 물건을 다시 물어보는 유일한 재시도
경로인데, 대상 선정에서 **status in ('종결','상세없음') or auction_result in ('낙찰','종결')이면 무조건
제외**한다. 즉 **낙찰(경매가 끝난) 물건은 애초에 재시도 대상이 아니다.** 이 함수의 목적은 "입찰예정
목록 화면의 정확도"이지 "sale_results/학습표본 완전성"이 아니라서, 부수효과로 **한 번 낙찰되면
그 물건의 0표본 시세는 영원히 고정된다.** _result_anomaly()도 이 케이스(시세 자체가 없음)는 걸러내는
종류의 이상이 아니라서 관여하지 않는다.

### 5. recorded_at은 생성 시각인가 갱신 시각인가

**갱신 시각이다.** upsert 구조(ON CONFLICT DO UPDATE SET, id 제외 전 컬럼)상 매 백필 실행마다 조건을
만족하는 행은 recorded_at이 그 실행 시각으로 덮어써진다. 134건이 전부 오늘 '2026-09-23 15:19:18' 하나의
값으로 뭉쳐 있는 것이 그 증거(서버 재시작 시 backfill_sale_results가 스레드로 도는 web/app.py:395).
09-08 22:41에 멈춘 4건은 "그날 이후 서버가 안 켜져서"가 아니라, **그 사이 해당 4개 vehicles 행의
median_price가 NULL로 바뀌어 조건을 더 이상 만족하지 못하게 됐기 때문**이다(3번 항목 확인 사실).
median_price가 왜 NULL로 바뀌었는지(재분석 실패로 덮어써진 것인지, 별도 초기화 로직인지)는 이번
조사 범위에서 원인 코드를 특정하지 못했다 — **미검증**.

### 6. 2026-08 '지난달 낙찰 실적' 창 영향

last_month_sale_stats()(web/service.py:4135-4165)는 db.list_sale_results()를 그대로 읽어
sale_date[:7]이 전월(오늘 기준 2026-08)인 행만 쓴다. 직접 대조했다.

| 구분 | 건수 |
|---|---:|
| vehicles: 낙찰+winning_price 보유, sale_date가 2026-08 | 193 |
| sale_results(비테스트) 중 sale_date 2026-08 | 100 |
| 그중 _valid()(카드가 실제로 쓰는 분모) 통과 | 100 |
| **커버리지** | **100/193 = 51.8%** |

193 = 100(포함) + 93(빠짐) — 3번 항목의 121건 중 93건이 정확히 이 8월 창에 속한다. **카드 제목은
"지난달 낙찰 실적"이지만 실제로는 지난달 낙찰의 절반만 대표한다.** 표본 수(100건)가 폴백 임계값(8건)을
가볍게 넘겨 90일 폴백은 발동하지 않으므로, 지금 이 순간 화면에 나가면 정확히 이 100건 기준으로 계산된다.

## [해석·추정]

1. [신뢰도 높음] 121건 결손의 직접 원인은 100% 동일 — 라이브 vehicles.median_price가 없다.
   포함 조건이 단순하고(1개), 재현이 정확히 맞아떨어졌다(257=136+121, 138=134+4).
2. [신뢰도 높음] 이 결손은 **설계(28건, 23%)와 결함/미비(93건, 77%)가 섞여 있다** — 순수 설계로만
   보기 어렵다. A(28)는 코드 주석으로 명문화된 의도. B(44)는 A와 같은 취지지만 키워드 목록이 불완전해
   분류만 못 된 경계 사례(사유 자체는 타당 — 경상용차는 실제로 동급 승용 시세가 없다). C(49)는 설계된
   근거가 코드 어디에도 없고, 오히려 requery_missing_market()의 주석이 "이 문제를 안다"고 스스로
   증언하면서도 낙찰 물건을 대상에서 제외해 **고칠 수 있는 길을 구조적으로 막아 놓았다.**
3. [신뢰도 중간] C의 31건(흔한 국산·수입 모델)이 08-17/18 집중 수집분과 겹치고, requery_missing_market
   주석이 언급하는 매핑 버그 수정 시점(09-10, 09-13)보다 앞선다는 점은, 이 0표본들이 "차가 특이해서"가
   아니라 "그때 매핑 코드가 미숙해서" 생겼을 가능성을 시사한다. 다만 당시 매핑 코드 자체를 비교 확인하지
   않았으므로 추정에 머문다.
4. [신뢰도 높음] sale_results(및 그걸 읽는 backtest_stats·last_month_sale_stats)는 **낙찰 전수가 아니라
   "매칭에 성공한 낙찰"만의 부분집합**이다. 배제된 쪽(B+C, 93건, 전체 121건 중 77%)이 경상용차·희귀
   수입차·매핑 실패 차종에 쏠려 있으므로, 남은 표본은 **구성이 무작위가 아니라 "흔한 국산차·매칭 잘
   되는 차종" 쪽으로 치우쳐 있다.** 낙찰가율 숫자 자체(비율)가 왜곡된다는 근거는 없지만, "이 통계가
   어떤 모집단을 대표하는가"는 카드 문구("지난달 낙찰 실적")가 암시하는 것과 다르다.

## [권고] — Steward가 판단할 때 고려할 사항

1. 분류 정정(작음, P2): no_market_reason()의 NEWCAR_SKIP_WORDS/NO_MARKET_HEAVY_WORDS에 포터·봉고·
   다마스·암롤트럭·음식물수거차 등 경상용차 키워드를 보강하면 B(44건)가 A로 합쳐져 "동급 시세 없음"으로
   정직하게 분류된다. 이건 sale_results 커버리지를 늘리지 않는다(애초에 시세가 성립하지 않는 차종이므로)
   — 표시 문구의 정확도 문제다.
2. 구조 결정 필요(핵심, P1): requery_missing_market()이 낙찰/종결 물건을 재시도 대상에서 빼는 것을
   그대로 둘지, 아니면 별도 예산으로 종결된 0표본 물건도 소량 재조회하게 할지는 승인이 필요한 정책
   결정이다(C.4 외부요청 한도와 얽힘). 이걸 하면 C의 31건(+파싱실패 18건 중 일부)이 회복될 가능성이 있고,
   sale_results·backtest_stats·'지난달 낙찰 실적' 커버리지가 개선된다.
3. 화면 문구(작음, P2): '지난달 낙찰 실적' 카드가 "표본 N건 기준"이라고만 적고 있다면(확인 필요), 그
   N이 실제 그달 낙찰의 몇 %인지는 적혀 있지 않다. 51.8%라는 숫자 자체를 노출할 필요는 없지만, "동급
   시세가 확인된 낙찰 기준"이라는 한정어가 이미 있는지 화면을 확인해 볼 가치가 있다.
4. PANEL-09 선행 조건: "유찰이 분모에서 빠진다"를 고치기 전에, 낙찰 쪽에서도 77%가 비무작위로 빠진
   결손을 먼저 인지하고 있어야 한다. 두 문제를 한 번에 섞어 고치면 어느 쪽 개선 효과인지 분리할 수 없다.
