## 2. 규칙 — 지시서 문언을 해석한 곳 (확인된 사실과 판단을 구분)

아래는 지시서 문언이 두 가지로 읽히거나 문언보다 한 걸음 더 간 곳이다. 모두 표나 설정 한 줄로 되돌릴 수 있다.

1. **'24시간 넘게 성공이 없으면' = 고장 상태가 24시간 이어짐**으로 읽었다. 근거는 S4 F4 의 권고 '예약 작업 `ok:false` 24시간 지속'이다. 다르게 읽으면 주간 작업이 매주 6일 동안 경보가 된다. 고장 시작 시각은 min(처음 본 시각, 실패한 마지막 실행 시각)으로 잡고 `data/org-state.json` 의 `task_bad` 에 적어 둔다. 매시 실패하는 작업은 마지막 실행이 늘 최근이라, 처음 본 시각이 없으면 24시간을 셀 수 없기 때문이다.
2. **예약 작업에도 '열린 티켓이면 만들지 않음'을 적용했다.** 지시서 문언에는 경보(①)에만 있었다. 적용하지 않으면 오늘 터널 작업이 AUD-05(열림, 오너 결재 중)와 겹치는 지시서가 된다. Steward 가 취소한 중복 11건과 같은 모양이다.
3. **정기 작업 표(패널·SSL·사진 점검)도 경보 입력에 넣었다.** F4 표의 '정기 작업 ❌·⚠ 줄 — 순환계가 읽나: 아니오'를 메우려는 것이다. 연속 기준은 공급 신호와 같다. 주간 작업은 '— 없음'인 날을 세지도 끊지도 않으므로 '연속 2편'이 **연속 두 회차**가 된다. 같은 원인을 다른 신호가 이미 보는 두 행(매일 갱신 → `실행 기록`, 집 회선 터널 → 예약 작업 + `엔카 시세`)은 §3.1 받는 자리 `-` 로 감시에서 뺐다.
4. ~~**'❔ 모름'인 날은 연속을 끊는다.** 서버를 못 읽은 날을 경보가 이어진 날로 치지 않는다. 그 대가로 지시서가 최대 하루 늦을 수 있다.~~
   **정정(r2, `reports/2026-09-27-ops3-backend-r2.md`)**: '최대 하루'는 틀렸다. 한 번 끊기면 2편을 새로 모아야 해서 2일 늦고, 14:00 넘어 만든 당일 리포트(❔ 지난 기간)가 하루걸러 끼면 지시서가 **아예 생기지 않았다**(QA-OPS3-3). r2 에서 규칙을 바꿨다 — 모름은 세지도 끊지도 않고, 끊는 것은 ✅ 정상뿐이다.

## 4. 멱등 키와 당직

- 경보 지시서 키는 `alert:<신호>:<연속 구간 첫 날짜>` 다. 같은 구간에서는 닫히거나 취소돼도 다시 만들지 않는다. 같은 신호의 열린 지시서가 있으면 새 구간이어도 만들지 않는다.
- 예약 작업 지시서 키는 `task:<작업>:<고장 시작>` 이다. 같은 작업의 열린 지시서가 있으면 만들지 않는다.
- 당직은 `alert`·`task` 지시서를 부르지 않는다. 문은 두 개다. 디스패치 계획에서 빠지고, `dispatch()` 로 손수 불러도 거부된다. §3.1 받는 자리를 자동 자리로 바꿔도 이 두 문이 막는다.
- 스탠드업에 '경보 → 티켓' 절이 생겼다. 신호마다 ❗ 티켓 없음 / 열린 티켓 / 지시서 번호를 적는다.
