# OPS-4 ④ 사내 대시보드 라벨 검수 — 경보 · 예약 작업 경보 · 건너뜀

[요약] 판정은 **조건부**다. 새 라벨 네 개는 영문 코드보다 분명히 낫고, 6개 폭 어디에서도 레이아웃이 무너지지 않았다. 경보의 주황도 빨강 '멈춤'과 갈린다. 남은 문제는 셋이다.

- **⑴ 같은 작업이 두 판정을 받는다.** backend ①이 만드는 '조용히 안 돎' 경보가 결재함에는 주황으로 서는데, 같은 화면 '정기 작업' 표에서는 초록 '정상'으로 그려진다. 코드로 확인했고 캡처는 없다. 계약 §3은 이 일을 OPS-4 ④에 걸어 두었다. 그래서 ④를 '완료'로 닫으려면 이 일을 하거나 따로 떼어야 한다.
- **⑵ 어휘가 두 벌이다.** '예약 작업 경보'가 가리키는 목록을 이 화면은 '정기 작업'이라고 부른다.
- **⑶ 기록이 조치보다 크게 보인다.** '건너뜀' 라벨이 피드에서 가장 밝은 글자다.

## 0. 조건 — 무엇을 어떻게 봤나

- **캡처:** `screenshots/ops4/` 19개를 전부 Read 로 열었다.
  - PNG 16장: before 6 · after 6 · x2 4
  - measure JSON 2개, HEAD.txt
  - 기준 커밋은 `e772962` 다(작업 트리 dirty, HEAD.txt). 이 검수를 시작할 때 HEAD 도 `e772962` 였다.
- **캡처 범위:** '흐름' 절만 찍혀 있다(KPI 4개 · 지시서 표 · 피드).
  - '정기 작업' 표, KPI '정기 작업' 타일, 공급 띠는 **캡처에 없다.** 그 부분의 판단은 코드를 읽고 한 것이다.
- **before/after 비교:** md5 는 다시 계산하지 못했다(이 자리에 셸이 없다).
  - 대신 6개 폭 12장을 모두 열어 라벨 글자가 실제로 바뀐 것을 눈으로 확인했다.
  - before 는 `alert`·`task`·`result.skipped`·`handoff.skipped`·`**` 였고, after 는 한국어 라벨이며 별표가 없다.
  - '마지막 순환' 표시도 1분 전 → 3분 전(320 은 2분 전)으로 바뀌었다. 그래서 frontend 보고대로 해시 차이만으로는 증명되지 않고, 글자로 증명된다.
- **대상 분기가 실제로 그려졌나:** 그렇다. alert 2 · task 1 · skipped 2 건이 `scan()` 실제 경로로 만들어졌다. `after-measure.json` 에 렌더된 글자와 계산된 색이 있다. 공허 통과가 아니다.
- **pytest:** 돌리지 않았다(이 자리에 실행 도구가 없다). 테스트 수치는 frontend 보고 값이라 **내게는 미검증**이다. 테스트 파일 `tests/test_ops4_dashboard_labels.py` 는 읽었다.
- **대비:** WCAG 상대휘도로 직접 다시 계산했다.

## ① 판정 — 조건부

- **지금 반영해도 되는 것:** 라벨 네 개, 피드의 경보 주황, `**` 떼기.
  - 이 로컬 도구는 요청마다 HTML 을 다시 읽는다. 그래서 오너 PC 에는 이미 반영돼 있다(frontend §5-8).
- **조건:** OPS-4 ④를 '완료'로 닫기 전에 둘 중 하나를 한다.
  - 아래 #1 을 한다.
  - 또는 분리 티켓을 만들고, 계약 §3 문장 "대시보드 정기 작업 표에는 이 판정이 아직 없다(OPS-4 ④)" 의 포인터를 그 번호로 바꾼다.
  - 이유: 부분 해결을 '완료'로 쓰지 않는다(CLAUDE.md 규칙 7).
- **시급도:**
  - `orders/` 에 reason task·alert 지시서는 아직 **0건**이다(grep `^reason: (task|alert)`).
  - 그런데 매시 스캔은 작업 트리의 `tools/org_runtime.py` 를 그대로 돌리고, 그 파일에 `silence_verdict` 가 이미 있다.
  - 그래서 첫 '조용히 안 돎' 지시서가 생기는 순간 #1 의 모순이 화면에 선다.

## ② 고칠 것 — 우선순위순 3건

### #1 같은 작업이 결재함에서는 주황 '예약 작업 경보', 정기 작업 표에서는 초록 '정상'

**화면·요소:** 사내 대시보드 결재함 표(task 행), '정기 작업' 절 표, KPI '정기 작업' 타일

**현재** — 코드로 확인했다. 캡처는 없다.
- backend ① `org_runtime.silence_verdict` 는 다음 조건을 모두 채운 작업을 고장으로 보고 task 지시서를 만든다.
  - 결과 0
  - 다음 실행이 잡혀 있음
  - 마지막 성공이 한도를 넘음(매일 36시간 · 매주 8일 · 매월 35일)
  - 위치: `if not t.get("ok") or not t.get("next_run"): return no` 다음 분기
- 표 렌더(`$('#sched').innerHTML` 블록)는 `s.ok ? '<span class="pill ok">정상</span>'` 이다.
- 타일(`kpi('정기 작업'`)은 `sched_never`·`sched_bad` 만 본다.
- 결과: 같은 작업이 표에서는 초록 '정상', 타일에서는 '정상'으로 선다.
- 계약 §3(작업 트리)은 이 일을 "(OPS-4 ④)" 로 ④에 걸어 두었다. frontend 도 §5-1 에서 같은 위험을 적었고, 필드 이름이 정해지지 않아 미뤘다.

**목표**
- 서버가 `silence_verdict` 결과(`bad`·`label`)를 `read_schedule` 행이나 `/api/state` 에 싣는다. 판정 함수는 하나로 둔다(계약 "같은 목록·같은 규칙").
- 표에는 `pill warn` 으로 '조용히 안 돎 · 마지막 성공 MM-DD HH:MM' 을 그리고, 행 클래스는 `late`(주황 배경)로 둔다.
- 타일은 주황(`'warn'`)으로, 부제는 "N개 조용히 안 돎"으로 둔다.
- 빨강은 지금처럼 '실패'와 '실행된 적 없음 · 예정도 없음'에만 쓴다.
- 이렇게 하면 결재함의 주황 라벨과 표의 주황 칩이 같은 톤, 같은 말(`label`)이 된다.

**함께 고칠 주석**
- 거짓인 문장: `.ord .rs.warn` 위 CSS 주석과 `tests/test_ops4_dashboard_labels.py` 머리 docstring 의 "빨강은 공급 '멈춤'에만 쓴다".
- 이 화면에서 빨강은 이런 곳에도 쓴다.
  - 정기 작업 '실패' 칩 · `tr.bad` · KPI 타일(`k.sched_never > 0 || k.sched_bad > 0`)
  - 리듬 '끊김'·'없음'(`RCLS`)
  - 맥박 굳음(`.beat.dead`)
  - 호출이 없는 자리(`.ag.never .cnt`)
- 고칠 문장: "빨강은 사실 판정(멈춤·실패·끊김)에만 쓴다 — 지시서 사유(결정 대기)에는 쓰지 않는다".
- 위험(추정): 지금 주석을 믿고 누군가 '실패' 칩을 주황으로 내리면, 표가 고장을 실제보다 약하게 보여 준다.

**근거:** 계약 §3 "같은 목록·같은 규칙", CLAUDE.md 규칙 7(부분 해결은 분리)

**담당**(워크플로 밖 독자를 위해 적는다)
1. backend-engineer: 판정을 행에 싣는다.
2. frontend-engineer: 렌더한다.

### #2 '예약 작업 경보'가 가리키는 목록을 이 화면은 '정기 작업'이라 부른다

**화면·요소**
- 결재함 사유 라벨 '예약 작업 경보'는 캡처에 있다.
- 스케줄러 절 제목 `<h2>정기 작업 <small>schtasks 실측</small></h2>` 와 KPI `kpi('정기 작업'` 은 캡처에 없다(코드로 확인).

**현재** — 코드로 확인했다.
- **계약 정의와 반대다.** 계약 §3.1 '신호' 정의는 이렇다: "정기 작업은 일일 리포트 `## 정기 작업` 표의 작업 이름, 예약 작업은 작업 스케줄러의 작업 이름". 그런데 대시보드는 스케줄러 목록을 '정기 작업'이라고 부른다.
- **경보를 따라가면 길이 끊긴다.**
  - 경보 목적 줄은 ``경보 `{name}`({source})`` 형식이고, source 는 '공급' 또는 '정기 작업'(일일 리포트 표)이다.
  - 결재함에 "경보 집 회선 터널(정기 작업)" 이 서면, 오너는 아래 '정기 작업' 표에서 찾게 된다.
  - 그런데 그 표에는 `naechaget-home-tunnel` 같은 스케줄러 이름만 있다(추정: 오너 동선).
- **'정기'를 세 가지가 나눠 쓴다:** 일일 리포트의 정기 작업, 대시보드의 스케줄러 표, 결재함 사유 '정기'(routine = 정기 점검 지시서, 캡처 05·06행).
- **같은 화면 안에서도 이미 갈렸다:**
  - 맥박 타일: "예약 작업 naechaget-org-heartbeat 확인"
  - 표 빈 상태: "예약 작업을 읽지 못했다."
  - 이 두 곳은 이미 '예약 작업'이라고 쓴다.
- **Steward 체크리스트도 섞였다:** `.claude/commands/daily-check.md` 는 "정기 작업 표"(일일 리포트) 바로 다음 줄에 "대시보드 정기 작업 표"(스케줄러)를 쓴다.

**목표:** 스케줄러 목록의 이름을 '예약 작업' 하나로 맞춘다.
- `tools/agent_dashboard.html`
  - 절 제목 → `예약 작업 <small>schtasks 실측</small>`
  - KPI → `kpi('예약 작업'`
  - 주석 세 곳: "정기 작업 표와 **같은 목록**" 두 곳(`heartbeatTile` 위, `renderFlow` 안), `// 정기 작업 — 한 번도 안 돈 것을`
- 같은 뜻의 포인터 → 모두 "대시보드 예약 작업 표" 로 바꾼다.
  - 계약 §3 의 "사내 대시보드 정기 작업 표" 두 문장
  - `schedule_verdict` docstring
  - org_runtime 주석 `# ── 예약 작업 — 대시보드 정기 작업 표`
  - org_runtime 주석 `# ⑦ 예약 작업 고장 → 결재함` — '고장'도 '경보'로 바꾼다. 조용히 안 돈 작업을 포함해야 해서다.
  - daily-check.md 의 "대시보드 정기 작업 표"
- 테스트 영향(읽기로만 확인했다):

**근거:** 계약 §3.1 정의, 이 화면의 기존 원칙 "타일 이름과 표의 어휘를 맞춘다"(`kpi('리듬 이상'` 위 주석)

### #3 '건너뜀' 라벨이 피드에서 가장 밝은 글자다 — 기록이 조치보다 크게 보인다

**화면·요소:** 피드 `.feed .k` 의 '인계 건너뜀'·'반려 판정 건너뜀'(캡처에 있다)

**현재** — 캡처와 측정으로 확인했다.
- `after-measure.json` 전 폭에서 두 라벨의 색은 rgb(230,237,243)(`--ink`), 굵기는 600 이다.

| 글자 | 대비 |
|---|---|
| 건너뜀(`--ink`) | **14.6:1** |
| 본문 `.x`(`--soft`) | 7.8:1 |

| 초록 '완료' | 약 6.8:1 |

- 착수·취소·당직 호출·당직 끝도 함께 조용해진다. 모두 '기록'이라 한 벌이 된다.

## ③ 잘된 점

1. **라벨표를 순환계 소스에 맞대는 테스트.**
   - 소스에서 `reason="…"`·`emit`·`skip`·`order.<상태>` 를 뽑아 RSN·EVK 와 대조한다.
   - 다음에 사유가 늘면 영문 코드가 화면에 서기 전에 테스트가 먼저 빨개진다.
   - 블록은 줄 번호가 아니라 `const RSN = {` … `};` 앵커로 자른다.
2. **'고장' 대신 '경보'.**
   - Steward 결정(조용히 안 돈 작업도 이 사유로 온다)에 맞춰 '고장'을 피했다.
   - 지시서 문언 '예약 작업 고장'보다 정확하다. 계약 §3 의 어휘 그대로다.
3. **경보 톤이 결재함 한 벌 안에 있다.**
   - 주황 굵게(600), 결재함 행 위 대비 6.88:1 이다. 내 계산도 같다.
   - 같은 행의 다른 사유(흐린 글씨, 굵기 400)와 확실히 갈린다.
   - 주황 KPI '결재함 3건', 결재함 행 배경과 같은 뜻('오늘 결정할 것')으로 묶인다.
   - 같은 행 목적 줄의 빨간 정지 이모지('멈춤')와 색이 다르다. 그래서 결정 대기와 사실이 다른 층으로 읽힌다.
4. **피드까지 넓힌 판단이 맞다.**
   - before-flow-1440 에서는 피드 맨 위 다섯 줄이 전부 파란 '지시서'였다. 경보 셋이 정기 점검과 구별되지 않았다.
   - after 에서는 결재함 표와 같은 주황 라벨이다. 한 사건에 한 톤이다.
   - 되돌리기도 한 줄이다.
5. **`**` 떼기.**
   - before 에서는 결재함 맨 윗줄에 "**2개 리포트 연속**"·"**273시간째**" 의 별표가 그대로 보였다.
   - after 는 깨끗하다.
6. **검증이 정직하다.**
   - 해시 차이가 '마지막 순환' 분 표시 때문에도 생긴다는 것을 스스로 적고, DOM 글자로 증명했다.
   - HEAD.txt 에 기준 커밋과 다른 담당의 dirty 파일을 남겼다.
   - 데이터를 `scan()` 실제 경로로 만들어 대상 분기가 실제로 그려졌다.
7. **레이아웃이 안정적이다.** 6개 폭 모두 가로 스크롤이 없고 화면 밖 요소가 0 이다(측정 JSON). 눈으로 봐도 무너진 곳이 없다.

## 질문별 답

**낱말 — 오너가 한눈에 이해하는가**
- **'경보':** 이해된다. 목적 줄도 '경보'로 시작해 서로 맞물린다.
- **'예약 작업 경보':** 뜻은 통한다. 다만 그 목록을 이 화면이 '정기 작업'이라 불러서 찾아가는 길이 끊긴다(#2).
  - 참고: 지시서는 이 라벨을 '예약 작업 고장'으로 적었지만 구현은 '경보'다. 구현 쪽이 맞다(잘된 점 2).
- **'인계 건너뜀'·'반려 판정 건너뜀':**
  - 넓은 폭에서는 뒤에 붙는 설명과 함께 읽혀 통한다.
  - 좁은 폭에서는 라벨만 남아 '누락'으로 읽힐 수 있다(추정).
  - 톤을 먼저 낮추고(#3), 낱말 교체는 선택으로 둔다(메모 4).

**톤 — '멈춤'·'정상'과 구분되는가**
- **'멈춤'과는 갈린다.** 빨강 #f85149 와 주황 #d29922 는 색상이 다르다(캡처: 정지 이모지 옆).
- **'정상'과는 색으로 갈린다.** '정상'은 초록 칩이다(코드). 하지만 조용히 안 돈 작업은 같은 작업이 두 판정을 받는 구조라 문제가 된다(#1).

**한 벌인가**
- **색:** 한 벌이다. 주황은 결정 대기를 뜻한다.
- **어휘:** 아직 두 벌이다('정기 작업'/'예약 작업', #2).
- **무채색:** 무채색 라벨이 가장 밝게 서는 것은 기존 규칙인데, 새 라벨이 들어오면서 드러났다(#3).

## 메모 — 범위 밖 · 기존 · 선택

1. **(backend, 캡처 전 폭에 보인다)** task 목적 줄에 "다음 실행 없음"이 두 번 나온다.
   - 화면 문장: "… 결과 3221225477(0xC0000005) · 다음 실행 없음 · 273시간째(마지막 실행 2026-09-16 05:24 · 다음 실행 없음)"
   - 원인: ``purpose=(f"예약 작업 `{t['name']}`"`` 에서 `{t['label']}` 이 이미 "· 다음 실행 없음" 으로 끝나는데, 괄호 부분이 "다음 실행 {… or '없음'}" 을 또 붙인다.
   - "273시간째"는 무엇의 273시간인지 주어가 없다. "마지막 실행 뒤 273시간"이 낫다.
   - 결재함 맨 위 세 줄 중 하나라, 다음에 org_runtime 을 고칠 때 같이 고친다.
2. **(관찰, 320)** 피드 첫 줄 지시서 번호가 "2026-09…" 로 잘린다(after-feed-320-x2).
   - 원인: 가장 긴 주황 라벨 '예약 작업 경보'.
   - before 에서는 번호가 온전했다.
   - 로컬 PC 도구이고 번호는 표에도 있으니 이번에는 둔다.
3. **(기존)** 620px 이하 카드 배치에서 결재함 행 배경에 줄무늬 틈이 보인다(after-inbox-320·360-x2, before 도 같다).
   - 원인: 배경이 칸마다 따로 칠해진다.
   - 카드 모드에서 행 단위로 칠하는 것은 다음 기회에 한다.
4. **(선택)** '건너뜀' 낱말을 바꾼다면, 무엇이 빠졌는지보다 어디로 갔는지를 말하는 쪽이 오독이 적다.
