# MKT-1 — 판정 원칙(보수적 가정)을 사용자가 알 수 있게 — 문구 초안

[요약] Steward가 확인한 5개 항목 중 **① 사고 이력 미확인 시 사고 가정 ② 침수·전손 의심 시 예상가 보류
③ 유찰 뒤 최저가 재확인 전 예상값 보류 ④ 시세 표본·신뢰도 게이트** 넷을 코드·테스트·배포 커밋으로 직접
재현했다(아래 §1). 다섯째 '정확도 공개'는 이미 랜딩 히어로·증명 스트립·정직 배너·`/accuracy`에 충분히
노출돼 있어 새 문구가 필요 없다 — 그래서 신규 초안은 넷으로만 구성했다(지시서가 허용한 "3~5개" 범위 안).
랜딩·base.html·Play 자세한 설명·출시 노트 4개 표면에 넣을 문구 초안을 §2에, 문장별 근거·배포상태·
표시광고법/Play 정책 리스크를 §3에 표로 냈다. **고정 수치는 어디에도 넣지 않았고, 시세 출처명·매물
링크도 쓰지 않았다.** 게시·배포·스토어 변경은 하지 않았다 — 전부 이 보고서 안의 초안이다.

## §2. 표면별 문구 초안

### 2-1. 랜딩(`web/templates/landing.html`) — '감으로 입찰하지 않습니다' 절

**넣을 위치**: "핵심 가치" 섹션의 3카드 그리드(`insights`·`description`·`shield` 아이콘 카드) **바로
뒤, section을 닫기 전** — 앵커는 셋째 카드 제목 "안전한 산정 로직" 바로 다음. 그 카드가 이미
"사고·침수 이력 시 자동 경고(입찰 중단 기준)"라고 한 줄로 요약한 것을, 아래 블록이 4가지로 구체화한다.
줄 번호로 가리키지 않는다 — 카드 제목 문자열로 찾는다.

**시각 제안(결정은 app-design-expert 몫)**: 바로 아래 "정직 배너"가 이미 큰 테두리 박스(`rounded-2xl`)
라서, 이 블록까지 같은 무게로 박스를 치면 박스 두 개가 연달아 나온다. 체크리스트형(가격 섹션의
무료 혜택 목록과 비슷한 가벼운 리스트)을 제안한다.

```
제목: 모르면 안전한 쪽으로 계산합니다
보조줄: 확인되지 않은 건 유리하게 보지 않습니다 — 나중에 무사고로 확인되면 득을 볼 뿐,
        손해를 보는 쪽으로는 가정하지 않습니다.

· 사고 이력을 확인하지 못한 차는 무사고로 보지 않고, 사고가 있다고 가정해 계산합니다.
· 침수·전손이 의심되는 차는 예상낙찰가 대신 "입찰하지 마세요"라고 알려드립니다.
· 유찰된 물건은 최저가가 법원 공고와 맞는지 다시 확인하기 전에는 예상값을 보여드리지 않습니다.
· 비교할 시세가 부족하거나 믿기 어려우면 숫자 대신 "표본 부족"·"미산출"로 표시합니다.
```

(제목 17자·보조줄 69자·항목 각 44~52자 — python `len()` 실측)

> 참고: "유찰"은 이 페이지에도 이미 쓰이는 말이고 설명 없이 노출돼 있다(기존 카드에도 없음). 상세
> 화면은 `ui.gloss()` 툴팁으로 같은 말을 풀어준다(`detail.html` "유찰횟수" 항목) — 랜딩에도 같은
> 패턴을 쓸지는 frontend·app-design-expert 판단에 맡긴다. 전문어를 아예 안 쓰기보다, 이미 이 앱의
> 기본 어휘인 것은 유지하고 필요하면 풀이를 다는 쪽이 일관적이라고 본다.

### 2-2. base.html — '이 앱은 무엇인가요?'/'서비스 소개' 블록

실제로는 두 군데다 — 데스크톱 사이드바(앵커: "참고용 분석 도구(투자 권유 아님)" 바로 뒤)와 모바일
푸터(앵커: "법원경매 분석 도구입니다 — 이 앱에서는 입찰할 수 없습니다." 바로 뒤, `w-full` 줄바꿈
패턴 재사용 가능). 둘 다 `/landing`으로 연결되는 링크만 있고 자체 설명은 없어서, 원칙 전체가 아니라
**한 문장짜리 티저**를 제안한다 — 전체 설명은 랜딩(2-1)에 있으니 중복을 피한다.

```
모르는 사고·침수는 안전한 쪽으로 가정해 계산합니다.
```
(29자)

양쪽에 같은 문장을 쓰는 것을 추천한다(일관성). 2문장째는 넣지 않는 것을 권한다 — 사이드바·모바일
푸터는 `text-xs`·`text-[11px]`로 이미 공간이 빠듯하고(CLAUDE.md가 기록한 320~360px 넘침 전례),
"더 보기"는 바로 옆 링크가 대신한다.

### 2-3. Play 자세한 설명 (`docs/STORE_LISTING.md`)

**넣을 위치**: "■ 이 앱이 다른 점 — 오차를 숨기지 않습니다" 절 **바로 뒤**, "■ 물건마다 계산해
드리는 것" **바로 앞**(두 신뢰 섹션을 묶어 앞세우고, 그다음에 기능 나열로 넘어가는 순서).

```
■ 모르는 건 안전한 쪽으로 가정합니다
· 사고 이력이 확인되지 않은 차는 '무사고'로 보지 않고, 사고가 있다고 가정해 계산합니다
· 침수·전손이 의심되는 물건은 예상낙찰가·입찰 상한선 대신 입찰을 멈추라는 경고를 보여 드립니다
· 유찰된 물건의 최저매각가는 법원 기일내역으로 다시 확인하고, 확인 전에는 예상값을 계산하지 않습니다
· 비교할 시세가 부족하거나 믿을 수 없으면 숫자 대신 '표본 부족'·'미산출'로 표시합니다
```

**길이 실측(python `len()`, 파일에서 직접 추출)**: 신규 섹션 240자. 삽입 후 전체 **1,491자 / 4,000자
한도**(여유 2,509자). ⚠ 문서에 적힌 현재 길이 "1,202자"는 내가 파일에서 직접 재추출해 측정하면
**1,251자**로 49자 차이가 있다 — 둘 다 python `len()`인데 다르다. 9/22 이후 본문이 소폭 수정되고
표기 줄을 안 갱신했을 가능성이 높지만 **원인은 미확인**이다. 4,000자 한도와는 무관(어느 쪽이든
한참 여유)하니 이 작업을 막지는 않지만, 이 문서를 다음에 또 고칠 때 표기 줄도 같이 갱신하는 편이
좋겠다.

### 2-4. 프로덕션 출시 노트 (`docs/STORE_LISTING.md` 해당 절, 500자 이내)

현재 노트에는 이미 P3(최저가 재확인) 한 줄이 있다("유찰된 물건의 최저매각가를 법원 기일내역으로
다시 확인하고…"). **P1·P2는 빠져 있다** — REC-9(침수 보류)가 오늘(10-01) 배포됐으니 "첫 정식
출시" 노트에 올릴 가치가 있다고 판단해 두 줄을 추가 제안한다.

```
· 사고 이력이 확인되지 않은 차는 사고가 있다고 가정해 보수적으로 계산합니다.
· 침수·전손이 의심되면 예상낙찰가 대신 입찰 중단 경고를 보여 드립니다.
```

위치: 기존 "· 유찰된 물건의 최저매각가를…" 줄 바로 뒤, "· 가격대·연식·주행거리 필터…" 줄 앞.
**실측**: 현재 268자 → 추가 후 **355자 / 500자 한도**(여유 145자). 둘 다 안 넣고 하나만 고르라면
P2(침수 보류)를 권한다 — 오늘 배포돼 가장 새롭고, 금전 손해를 직접 막는 기능이라 신규 설치 사용자가
가장 먼저 알아야 할 안전장치다.

### 2-5. 짧은 설명(80자) — 의견만 (초안 없음)

바꾸지 않는 것을 권한다. 현재 64자(80자 한도, 여유 16자)인데, 16자로는 "모르는 건 안전한 쪽으로
가정"류를 압축할 수 없다 — 억지로 줄이면 근거 없는 구호("안전합니다")처럼 읽혀 오히려 지시서가
금지한 과장에 가까워질 위험이 있다. 이 원칙은 공간이 있는 자세한 설명(2-3)과 랜딩(2-1)에서
설명하는 편이 맞다고 본다.

## §5. 권고 — 어디부터, 출시 일정과의 관계

**권고 순서**: ⑴ Store 자세한 설명(2-3)·출시 노트(2-4) 먼저 — 코드 변경이 필요 없고, PLAY-1이
"프로덕션 액세스 승인(09-30), 출시 전날 `store_final` → 출시 승인"으로 이미 출시가 임박했다(MEMORY
기준). 문구만 오너가 승인하면 콘솔 반영은 오너 손으로 바로 된다. ⑵ 랜딩·base.html(2-1·2-2)은
frontend-engineer 구현 → CLAUDE.md 화면 검수 4단계(측정·육안·`app-design-expert`·재측정, 공개
제품 화면이므로) → 배포 → 필요시 `06_landing.png` 재촬영, 순서로 **출시 전에 급히 넣기보다는
출시 직후 첫 업데이트로 가도 늦지 않는다.** Store 설명·출시노트가 이미 같은 메시지를 담아 신규
설치 사용자에게는 공백이 생기지 않는다.

**출시 일정과의 관계**: Store 쪽 변경(2-3·2-4)은 제출 전 오너가 콘솔에 반영하는 작업과 같은
타이밍에 묶을 수 있다. 랜딩·base.html 변경은 디자인 검수가 필요해 더 걸리므로, 둘을 같은 배포에
묶으려 하지 말고 **Store 문구를 먼저 승인·반영**하는 쪽을 권한다.
