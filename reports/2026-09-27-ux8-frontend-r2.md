## 2. B-2: 왜 MO인가
측정은 확인된 사실이다. 조건은 Chrome 153, CPU 4배 스로틀, 매회 새 컨텍스트이고, rAF마다 `open`을 기록했다(qa `b_repeat`와 같은 절차). 대상은 넓은 폭 4종(1440a·1024a·768a·640a)과 390 펼침 기억이다.

| 시안 | 닫힌 프레임이 나온 실행 수 |
|---|---|
| r1 (`</details>` 뒤) | 12/25, 26/50 |
| `</summary>` 바로 뒤 (사이 공백 0) | 10/25 |
| details 첫 자식 (qa 후보) | 7/25 |
| **MO** | **0/25, 0/50** |
| 390 기본(접힘) | 전 시안 0 |

- Slow 3G + CPU 4배(N=2, 전체 스위트가 동시에 돌던 상태): r1은 10/10, MO는 0/10이었다.
- **qa 후보에는 결함이 하나 더 있다.** 스크립트가 도는 시점에 summary가 아직 없어서 클릭 리스너가 붙지 않는다. 그래서 펼침 기억이 한 번도 써지지 않는다. key 수정을 넣은 상태에서도 B-1 테스트 2건과 P11 2건이 실패했다.
- **분할 전송 P12를 새로 넣었다.**
  - 끊는 자리: details 여는 태그 뒤, summary 뒤, details 뒤.
  - 화면: 640·1440 넓은 폭, 폰 펼침 기억, 폰 기본.
  - 결과(12칸): MO 12/12 통과, r1 9칸 실패, summary 뒤 시안 6칸 실패, 첫 자식 시안 3칸 실패.
  - qa의 `test_b2`는 details 뒤에서만 끊어서 summary 뒤 시안도 통과시킨다. P12가 그 사각을 메운다.
- **원인은 추정이다.** 스크립트를 폼 뒤에서 summary 바로 뒤(사이 토큰 0개)로 옮겨도 비율이 줄지 않았다. Chromium이 파서 차단 인라인 스크립트를 실행하기 직전에 양보한다고 보고 있지만, 소스로 확인하지는 않았다.
- **MO가 막는 이유는 명세 근거와 측정이다.** 관찰 콜백은 마이크로태스크다. HTML 이벤트 루프에서 렌더링은 태스크가 끝나고 마이크로태스크를 다 비운 뒤에만 일어난다. 실기기(TWA·안드로이드 Chrome·삼성 인터넷)에서는 확인하지 않았다.
- **대가는 두 가지다.**
  - summary 클릭은 details에 위임해서 받는다(`closest('summary')`이고 `parentNode===d`인 경우만).
  - MutationObserver가 없는 브라우저는 DOMContentLoaded에서 정한다.
  - 키보드 Enter, 탭 복귀, 스크롤 복원 순서 테스트는 모두 초록이다.
