## [요약]

**지시서의 전제가 뒤집혔다.** 2025타경53062_1 은 침수차가 아니다 — 감정요항 원문이
*"전손, 도난, 침수 보험사고 이력 및 특수용도 이력은 **없는 것으로 조회되었음**"* 이라고 적혀 있다(확인된 사실, 로컬 원문).
라이브의 `accident_grade='none'` 이 **맞는 값**이고, 로컬 사본의 `'flood'` 는 2026-09-21 파서 수정(`e093524`·`8e51252`·`1b708d8`,
"진짜 침수인가" — 20대 중 14대 부정문 오독) **이전** 파서의 산물이다(행 `analyzed_at` 2026-08-20, 사본 전체 최신 `analyzed_at` 2026-09-17 —
사본은 9/21 수정 이전 상태). 라이브에서 침수 경고가 없는 것은 결함이 아니라 정정이다.

남은 진짜 불일치는 **`condition_flags` 의 "침수" 가 재파싱되지 않고 낡은 채 남은 것**(라이브·로컬 모두)과,
그 반대 방향으로 **보험이력 카운트가 있으면 자유서술의 진짜 전손을 건너뛰던 게이트**(2026타경10406_1, 종결) 하나다.
지시서 대안 (a) "플래그의 침수도 flood 로 본다" 는 **채택하지 않았다** — 그 플래그 18행 중 11행이 부정문 오독이라, 채택하면
"침수 없음"이라고 적힌 차 11대에 거짓 STOP 이 붙는다(아래 §3).

### (b) bid_state 가 침수를 판단하는 열 (확인된 사실)

`service.bid_state` 앵커 `if v.get("accident_grade") == "flood" or v.get("judgment") == "입찰 보류":` → `blocked / 침수·전손 의심 — 입찰 보류 / stop`.
**`condition_flags` 는 보지 않는다.** 침수 원천은 둘: ① `accident_grade`(grade_accident) ② 저장 문자열 `judgment`(calculate → `_is_flood` = 등급 flood 또는 `_strip_report` 후 키워드).
`condition_flags` 는 `_appraisal_signals`(parse_appraisal) 가 별도 키워드 스캔으로 만들며, 템플릿 어디에서도 렌더되지 않는다(`grep condition_flags web/templates` 0건).
즉 침수 원천이 **셋**이었고, 셋이 서로 다른 시점·다른 규칙으로 갱신됐다.

## 3. 최소 수정안 — 구현한 것 / 하지 않은 것

원칙: **침수 여부의 원천을 `grade_accident`(accident_grade) 하나로.** 판정 규칙(`bid_state`)은 건드리지 않았다.

### 구현 (3파일, 스키마 변경 없음)

1. `src/parse/appraisal.py` — `"침수"` 를 `_DAMAGE_MAJOR`(→ `condition_flags`) 에서 빼고 `_LEVEL_ONLY_KW` 로 옮김. 등급(poor) 계산에는 그대로 반영.
   실측: 1,309건 파싱 결과 **level 변화 0건**, 플래그에서 "침수" 가 빠지는 행 7건(전부 `accident_grade='flood'` — 판정은 등급이 이미 stop).
   → `condition_flags` 가 **더 이상 독립적으로 침수를 주장하지 않는다.** 완화 아님(level 동일, 판정 미변경).
2. `web/service.py` — `backfill_appraisal_signals`: `condition_flags` 에 "침수" 가 남은 행은 `condition_level` 이 있어도 다시 읽는다(`_stale_flood_flag`).
   현재 파서는 그 플래그를 만들지 않으므로 한 번 읽으면 사라짐(멱등, 두 번째 호출 0건 — 테스트로 고정). 기동 시 자동 실행(무네트워크)이라 배포 후 첫 기동에서 라이브 53062_1 류가 정리된다.
   함께 경로를 `os.path.join("data", …)` → `src.paths.DATA_DIR` 로(다른 백필과 같은 원천; 상대경로는 cwd 가 바뀌면 조용히 0건).
3. `src/parse/detail_parser.py` — `grade_accident` 의 `if not report_present:` 게이트 제거. 자유서술 침수·전손을 카운트 유무와 무관하게 본다.
   실측: 1,340건 중 flood 판정이 바뀌는 행 **1건(2026타경10406_1, 진짜 전손, 종결)**, 부정문 11건은 그대로 none/accident. **강화만**(none/accident → flood 방향만 가능).
   `calculator._is_flood` 와의 불일치 1 → 0.

### 채택하지 않은 것과 이유

- **지시서 (a) `bid_state` 가 `condition_flags` 의 "침수" 도 flood 로 본다** — 기각. 그 플래그는 ① 현재 파서에선 생성되지 않고 ② 남은 것은 옛 파서의 부정문 오독이다(18행 중 11행).
  채택 시 감정요항이 "침수 없음" 이라고 적은 차 11대(라이브 추정 ≥11)에 `침수·전손 의심 — 입찰 보류` 가 붙어 9/21 사용자 지적("진짜 침수인가")을 되살린다. 상세 화면은 요항 원문을 그대로 보여 주므로 사용자가 모순을 바로 본다. 이 결정을 `test_bid_state_reads_flood_from_accident_grade_not_condition_flags` 로 고정했고, 뒤집으려면 오너 승인 항목(§6).
- **지시서 (b) 문자 그대로 "파서/재분석이 flood 를 none 으로 덮어쓰지 못하게"** — 기각. 9/21 하향 22건(사본 재판정: flood→accident 16, flood→none 6)이 전부 옳은 정정이라 blanket 보호는 오탐을 동결한다. 대신 **잘못 내리는 유일한 경로**(게이트)만 막았다.
- `analyze_item` 의 "요항 비고 사진만 있으면 등급 none 덮어씀" 은 발생 실측이 없어(추정) 손대지 않았다. 후속 후보.
- `backfill_accident_grades` 의 NULL-median 행 judgment 미재산정(구조적 틈)은 사본 실측 영향 0건이라 손대지 않았다. 후속 후보.
- `service.py` 의 다른 상대경로 `"data"` 8곳(사진·지도 OCR 등)은 범위 밖.

## 5. 라이브 검증·배포 후 절차 (Steward 실행, 읽기 전용 → 승인 후 쓰기)

읽기 전용 확인(라이브 `sqlite3 "file:…/auction.db?mode=ro"`):
```sql
-- (1) 낡은 플래그 규모(추정 ≥11)
SELECT count(*) FROM vehicles WHERE condition_flags LIKE '%침수%' AND (accident_grade IS NULL OR accident_grade<>'flood');
-- (2) 53062_1 이 9/21 백필로 내려간 것인지(accident_hits·insurance_history 가 [] / {} 이고 analyzed_at 이 8/20 그대로면 백필, 9/21 이후면 재수집)

-- (3) 등급은 내려갔는데 judgment 가 남은 행(구조적 틈 — 0 이어야 함)

```
그리고 EC2 의 `data/2025타경53062_1/appraisal.txt` 에 "침수 보험사고 이력 … 없는 것으로 조회되었음" 문장이 있는지(로컬과 같은 원문인지) 눈으로 확인 — 같으면 §요약의 결론이 라이브에도 그대로 선다.

배포 후: ① `backfill_appraisal_signals` 는 기동 시 자동(무네트워크) — 낡은 플래그 정리. ② 10406_1 류 등급 재도출은 `backfill_accident_grades()`(수동, 무네트워크)를 돌려야 반영 — 등급이 flood 로 **올라가는** 행만 생기지만 판정 변경이므로 §6 승인 후.

## 6. 오너 승인 항목 (배포 전)

1. `grade_accident` 게이트 제거 — 판정 규칙 **강화**(보험이력 카운트가 있어도 자유서술 전손·침수 → flood). 사본 영향 1건(종결). 라이브에 반영하려면 `backfill_accident_grades()` 수동 실행 필요.
2. 지시서 대안 (a) 불채택 확정 — `condition_flags` 를 판정 원천으로 쓰지 않는다. 뒤집으려면 라이브 ≥11대가 거짓 STOP 을 받는다는 수치를 함께 놓고 결정.
3. `condition_flags` 값 변화 고지 — "침수" 낱말이 더 이상 들어가지 않음(스키마·API 키 변경 없음, 템플릿 미사용 확인). frontend 가 장래에 플래그를 그릴 계획이면 침수 표시는 `accident_grade`/`accident_label`("침수의심")을 써야 한다.

## 스키마 변경 여부

**없음.** DB 열·마이그레이션·API 응답 키 모두 그대로. 값 수준 변화: `condition_flags` 에 "침수" 미포함(위 6-3).
