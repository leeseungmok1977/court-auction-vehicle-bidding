## 정렬식 원문과 "오늘" 정의

```sql
-- SALE_DATE_SORT  (sort=sale_date)
ORDER BY CASE WHEN sale_date IS NULL THEN 2
              WHEN sale_date >= date('now','localtime') THEN 0 ELSE 1 END,   -- ① 0=오늘 이후(오늘 포함) 1=지난 기일 2=NULL
         CASE WHEN sale_date >= date('now','localtime') THEN sale_date END,   -- ② 미래 블록만 ASC(나머지 NULL=동률)
         sale_date DESC                                                       -- ③ 과거 블록에서만 실질 작용(최근 종료 먼저)

-- MILEAGE_SORT  (sort=mileage)
ORDER BY (mileage_km IS NULL OR mileage_km <= 0), mileage_km                  -- NULL·0 이하 한 블록으로 뒤, 양수 ASC

-- sale_date_asc (내부 기본값, 예전 그대로)
ORDER BY sale_date
```

- **"오늘"**: SQL 은 `date('now','localtime')` — `_vehicles_where` 의 `upcoming_days` 조각과 **같은 식**(PANEL-16: 자리는 하나
  늘었지만 식은 통일, 테스트 `test_sale_date_sort_uses_same_today_expression_as_upcoming_days` 가 지킨다). 파이썬(`sale_split`)은
  `vehicles()` 안에 이미 있던 `_tdy = _date.today().isoformat()` 을 그대로 쓴다. 둘은 같은 머신의 로컬 날짜라 같은 날을 가리킨다
  (테스트 `test_sql_today_and_python_today_agree` 로 실측; 자정 정각을 가로지르는 한 요청에서만 어긋날 수 있다 — 무시 가능).
  서버 TZ 를 KST 로 **가정하지 않았다** — 기존 코드의 관례(SQL localtime ↔ 파이썬 today)를 따랐다.
- 오늘 기일은 **미래 블록**(입찰 시각 전이면 아직 입찰 가능). 오늘 블록 안에서 첫 행이다.
- `sale_date = ''` 는 SQL·파이썬 모두 '지난 기일'로 분류된다(`'' >= 오늘` 거짓). 운영 DB 에 `''` 는 0행이라 실무 영향 없음.
- 동률(같은 sale_date) 안 순서는 규정하지 않았다(예전과 같음 — tie-break 를 새로 넣지 않았다).

## 계약 — frontend 가 그대로 쓸 명세

### `sale_split` (컨텍스트 키, `vehicles.html`)
```python
sale_split = None                                   # sort != "sale_date" 이거나 파이썬 경로(segment·bucket·usepick·picks)·sort=expected
sale_split = {                                      # sort == "sale_date" 이고 SQL 경로일 때만
    "upcoming": int,            # 필터 적용 후 모수에서 sale_date >= 오늘 (오늘 포함) 행 수
    "past":     int,            # sale_date < 오늘 행 수
    "undated":  int,            # sale_date NULL 행 수                     (upcoming + past + undated == total)
    "page_first_past_idx": int | None,
}
```
**`page_first_past_idx` 정의(보충 ② 원문)**: *전체 정렬 결과에서 첫 '지난 기일' 행의 전역 인덱스가 현재 페이지 범위
`[start, start+len(page_rows))` 안에 있을 때만 그 페이지 내 0-based 인덱스, 그 밖(경계가 앞 페이지에 있었거나 지난 기일이 없음)이면
None. 즉 구분 줄은 경계가 놓인 페이지에 한 번만 그려진다.*
- 화면 규칙: `sale_split and sale_split.page_first_past_idx is not none` 이면 `rows[page_first_past_idx]` **앞**에
  `지난 기일 · {{ sale_split.past }}건` 구분 줄. `page_first_past_idx == 0` 이면 첫 카드 위(전부 지난 기일인 필터 조합 포함).
- `undated` 는 구분 줄 대상이 아니다(NULL 은 맨 뒤에 있지만 "지난 기일" 이 아니다). 필요하면 별도 표기.
- 모수는 `총 N건` 과 같다(필터 적용 후, 페이지 슬라이스 전). `upcoming=30` 이면 past·undated 가 0 이고 인덱스 None.
- 운영 DB 사본(hide_incomplete 모수 1,163행) 기준 경계는 전역 144 → **13페이지 0번**. 1~12페이지는 None.

### `qs_no_date` · `qs_no_result` · `qs_no_court` · `qs_no_q` (컨텍스트 키, 문자열)
- 현재 URL 의 필터 전부(`_filters`: judgment·maker·q·sort·upcoming·result·status·cond·date·court·promising·segment·bucket·usepick·
  all·picks·price 중 값이 있는 것)에서 **그 키 하나만 뺀** urlencode 문자열. `qs_no_bucket`·`qs_no_price` 와 같은 관례.
- 사용: `<a href="/vehicles{% if qs_no_date %}?{{ qs_no_date }}{% endif %}">…✕</a>`. 키가 원래 없으면 `qs` 와 같다.
- `promising` 은 넣지 않았다(칩이 `judgment=…&sort=expected` 별도 링크).

## 못 한 것 / 판단을 남긴 것
- **segment·bucket 경로의 `sale_split`**: 두 경로는 SQL 순서를 보존하므로 구분 줄을 그릴 수 있으나, 지시서 ④("파이썬 경로 → None")를
  따라 일괄 None 으로 두었다. usepick·picks 는 순서를 다시 매기므로 None 이 맞다. segment·bucket 에서도 그리려면
  `not _py_filtered` 조건을 `not (usepick in USEPICK_VALUES or picks == "1")` 로 좁히면 된다(테스트 ④ 파라미터 2·4개 수정).

- `sale_date = ''` 를 미상으로 다루지 않았다(운영 0행). 생기면 `COALESCE(sale_date,'')=''` 로 SQL·파이썬을 함께 고쳐야 한다.
