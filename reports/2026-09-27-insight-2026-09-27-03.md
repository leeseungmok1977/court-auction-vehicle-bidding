## 1. ①~⑤ 결과 (insight 원문 요약, [사실]/[추정] 표기 유지)

**① 같은 모집단인가** — [사실(코드)] 아니다. `dxdy_history` 는 상세페이지 잠정 기록이고, 이미 분석된 물건은 상세를 다시 받지 않아
마지막 수집 시점에서 멈출 수 있다. `result_code=''`(약 53%, 인용 수치)에는 아직 열리지 않은 회차가 섞여 있을 수 있다[추정].
`sale_results` 는 매각결과검색(result_search)으로 확정한 낙찰뿐이다. → 둘을 합치지 말고, **result_search 가 이미 알아낸 유찰을
낙찰과 같은 방식으로 저장**하면 출처와 신선도가 같아진다.

**② 층별 무입찰 비율** — **측정 못 함.** `vehicles.fail_count`(법원 `yuchalCnt` 를 이미 저장) × `auction_result` GROUP BY 한 번이면
되는 쿼리지만 실행 권한이 없었다. 로컬 `data/auction.db` 는 09-23 15:27 스냅샷이다(insight `ls` 확인, 미재현). insight 는 원시 바이트를
grep 해 본 수치(572 vs 962)가 서로 맞지 않아 **스스로 폐기**했다 — freelist 에 남은 옛 값까지 세어진 것으로 본다. 그 수치는 이 보고에 쓰지 않았다.

**③ 선택편향 방향**
- [사실(수식)] 1차 편향: 무입찰 유찰이 분모에서 빠져 있어 표시 확률은 항상 **실제보다 낮다**
  (`P(실제) = P(무입찰) + (1−P(무입찰))×현재값 ≥ 현재값`). 사용자를 **더 높은 금액** 쪽으로 민다. PANEL-02 가 화면에 이미 고지했다.
- [추정, 신뢰도 낮음] 2차 편향(PANEL-17): 분모를 고쳐도 `sale_results` 가 건설기계·특장·경상용차를 체계적으로 빼는 문제는 남는다.
  방향은 이 데이터로 판단할 수 없다.

**④ 새 외부요청 필요 여부** — [사실(코드)] **필요 없다.** 2단계 핵심은 영구 기록(스키마) + `record_sale_result` 호출 옆에 유찰 분기
하나다. C.4 요청 상한에 영향 없음.

**⑤ PANEL-53** — [추정, 신뢰도 중간] 170건 중 이미 설명되는 123건(`median_price` NULL)을 빼면 47건이 남는다. 상세 파싱만으로 잠정 낙찰을
받은 물건이 45일 창(`_in_window`)을 벗어나 result_search 확정을 받지 못한 경우가 일부를 설명할 수 있다는 가설이다. 라이브 분해가 필요하다.

**부수 발견** — [사실(코드, insight 주장·Steward 미재현)] `web/db.py` 의 `sale_results.id` 주석은 `court_code|case_no|item_no` 형식이라고

## 4. 다음 담당이 그대로 돌릴 쿼리 (읽기 전용 사본에서, `mode=ro`)
```sql
-- ② 유찰 층별 결과 분포 (조건: result_source 별로도 나눠 볼 것)
SELECT CASE WHEN fail_count >= 3 THEN '3+' ELSE CAST(COALESCE(fail_count,0) AS TEXT) END AS tier,
       auction_result, result_source, COUNT(*) AS n
FROM vehicles
GROUP BY tier, auction_result, result_source
ORDER BY tier, auction_result;

-- "유찰 615건" 재검증 (dxdy_history 저장 형식은 스키마 확인 후 맞출 것)
-- PANEL-53: 잠정 낙찰인데 sale_results 에 없는 물건
SELECT v.result_source, (v.median_price IS NULL) AS no_median, COUNT(*)
FROM vehicles v LEFT JOIN sale_results s ON s.id = v.id
WHERE v.auction_result = '낙찰' AND s.id IS NULL
GROUP BY 1, 2;
```
